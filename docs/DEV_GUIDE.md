## 0. 3분 요약

**한 줄로**: 코드를 읽지 못해도 안전하게 만들 수 있게 한다. 방법은 네 가지다. 일을 작게 나누고, 테스트를 먼저 쓰고, **한국어 수용 시험 결과**로 승인하고, **숫자 관문**을 통과한 것만 돈에 닿게 한다.

| 주제 | 핵심 | 절 |
|---|---|---|
| 개발 방식 | 폰의 Claude 앱 Code 탭(클라우드 세션)에서 **작업 카드 1장 = PR 1개**로 일한다. 테스트를 먼저 쓰고, PR은 diff가 아니라 수용 시험 결과로 승인한다. 주문·가드 코드는 작성 세션과 다른 **리뷰 세션**이 검토한다 | §1 |
| 순서 (D16) | 0 준비·게이트 → 1 데이터·지표 → **2 G1 백테스트(Go/No-Go)** → 3 Claude 섀도 + 텔레그램(주문 없음), G3 페이퍼 시작 → 4 주문 게이트웨이·리스크 가드(G3와 병행, G2) → 5 운영 강화 → 6 소액 실거래 G4 → 7 확대 G5 | §2 |
| 저장소 | 비공개, `main` + 짧은 작업 브랜치, 스쿼시 병합, CI를 통과한 태그만 배포 | §3 |
| 코딩 규칙 | 시각은 UTC, 마감된 봉만 사용, 공용 모듈은 순수 함수, 주문 자동 재시도 금지, 모르면 주문 안 함(fail-closed), 가격·수량은 코드가 계산 | §4 |
| 테스트 | 불변조건 16개 → 단위 → 통합(저장한 데이터와 가짜 응답) → 재생 동등성 → 수용 시험 → 테스트넷 G2 → 페이퍼 G3 | §5 |
| 백테스트 | 규칙·변형을 먼저 문서로 고정한다. 공용 체결 모델에 비용·펀딩·승인 지연·가용성을 넣는다. 워크포워드로 검증하고, 무작위·일봉 돈치안 기준선과 비교하고, 모든 시도 수를 기록한다. Claude 층은 과거 백테스트를 하지 않는다 | §6 |
| LLM 평가 | 패스·차단된 신호까지 모두 R로 채점한다. Claude 의견과 코드 메타 필터를 약 600건에서 비교하고, 확신도는 Brier 점수로 본다. 프롬프트는 버전별로 고정한다 | §7 |
| 실거래 전환 | D17 (1)~(5)를 모두 충족하고, 사용자가 결정 기록에 서명한다. 적중률 기준은 쓰지 않는다 | §8 |
| 학습 | 단계마다 "이것만 알면 된다" 개념 목록과 자기 점검 질문을 둔다 | §9 |

**이 문서를 쓰면서 새로 확인한 사실 3가지** (기존 문서에 없던 내용)

1. **개인 계정의 비공개 저장소에서는 GitHub 보호 기능 일부를 무료로 쓸 수 없다.**
   - 이 저장소의 소유자는 개인 계정이다(`"type": "User"`) [1][직접].
   - 무료 개인 계정에서 **브랜치 보호, 룰셋, CODEOWNERS**는 공개 저장소에서만 제공된다. 비공개 저장소에서 쓰려면 GitHub Pro 이상이 필요하다 [2][3][4][직접].
   - **GitHub 비밀 스캐닝**은 사용자 소유 비공개 저장소에 제공되지 않는다. 예외는 Enterprise Managed Users와 Enterprise Server다 [5][직접].
   - 그래서 D15의 "비공개 전환 + Secret scanning·push protection + main 브랜치 보호"는 무료 개인 계정에서 **한꺼번에 성립하지 않는다.** 비공개 전환(D15)은 그대로 권고한다. 비밀 유출 방어는 **gitleaks(pre-commit + CI)가 1차 방어선**이 된다. 브랜치 보호는 GitHub Pro 구독 또는 보완 통제 중에서 고른다(§3.4, **[결정 필요]**).
2. **gitleaks는 "기능 완성, 앞으로 보안 패치만" 상태다.** 저장소 README가 "Gitleaks is feature complete … Future releases will be security patches only"라고 적었다 [9][직접]. 유지보수가 끊긴 것은 아니다. 다만 대체 도구를 연 1회 재평가한다(§10).
3. **CLAUDE.md는 지침일 뿐 강제 설정이 아니다.** Claude Code 공식 문서는 CLAUDE.md를 "context, not enforced configuration"이라고 적는다. 반드시 막아야 하는 동작은 hook이나 권한 설정으로 막으라고 한다 [12][직접]. 그래서 이 가이드의 규칙은 **CI·테스트·서버 설정으로 강제**하고, CLAUDE.md는 안내용으로만 쓴다(§1.8).

**개발 전에 사용자가 할 일**: PLAN §11의 결정 10개와 이 문서 §10.1의 결정 1개에 답한다. 나머지는 추천값이 적용돼 있다.

## 1. 바이브코딩 원칙

바이브코딩은 사람이 말로 지시하고 AI가 코드를 쓰는 방식이다. 사용자는 코드를 읽을 수 없다. 그래서 "PR diff를 검토한 뒤 병합"은 형식적 승인이 된다 [SEC-06+F09]. 이 절은 **코드를 읽지 않고도 결과를 판정하는 방법**을 정한다.

### 1.1 누가 무엇을 하나

| 주체 | 하는 일 | 하지 않는 일 |
|---|---|---|
| **사용자** | 작업 카드 우선순위 정하기, 수용 시험 직접 해 보기, PR 병합, 태그 만들기, 서버에서 배포 명령 실행, 관문 판정 서명 | 코드 한 줄씩 읽기(필요 없음), 폰으로 한도 완화·정지 해제 |
| **작성 세션** (Claude Code 클라우드) | 테스트 → 코드 → PR 생성. PR 본문에 수용 시험 결과와 "처음엔 실패했던 테스트" 목록을 적는다 | 웹 가져오기(WebFetch), 허용목록 밖 패키지 추가, 카드에 없는 보호 경로 수정 |
| **리뷰 세션** (작성 세션과 다른 세션) | 보호 경로가 바뀐 PR을 §1.6-B 체크리스트로 검토하고, 결과를 `docs/reviews/PR-<번호>.md`로 남긴다 | 코드 수정(지적만 한다) |
| **조사 세션** | 외부 문서를 읽고 `research/`에만 쓴다 | `src/`·`tests/` 수정 |
| **CI** (GitHub Actions) | pytest, ruff, gitleaks, pip-audit, 허용목록 검사, 보호 경로 검사, `uv sync --locked` | 서버 접근, 비밀 보관 |
| **서버** | CI를 통과한 태그만 실행한다 | 코드 수정. 서버에는 Claude Code를 두지 않는다 (INFRA §1.2) |

### 1.2 원칙 10가지

1. **작게 나눈다.** 작업 카드 1장 = PR 1개 = 목적 1개다. 크기 기준(제안): 테스트·픽스처를 뺀 코드 변경 300줄 이하, 파일 10개 이하, 수용 시험을 30분 안에 할 수 있을 것. 넘으면 카드를 나눈다.
2. **테스트를 먼저 쓴다.** 실패하는 테스트를 먼저 만들고, 구현해서 통과시킨다(§1.4). 불변조건 테스트(ARCHITECTURE §2.4)는 해당 코드보다 **먼저, 별도 PR로** 들어간다 [SEC-06].
3. **PR은 수용 시험 결과로 승인한다.** "이렇게 하면 이렇게 돼야 한다"를 한국어로 적고, 실제 결과를 표로 붙인다. 사용자는 최소 1개를 직접 해 본다 [SEC-06+F09].
4. **숫자는 결정표를 가리킨다.** 설정 파일에 값을 넣을 때 옆에 결정표 ID(예: `D8`)를 주석으로 단다. 문서끼리 값을 복사하지 않는다 [Q4+F10].
5. **한 번에 하나만 바꾼다.** 특히 규칙 파라미터, 프롬프트, 스키마가 그렇다. LLM은 형식만 바꿔도 결과가 크게 흔들린다(구형 모델에서 최대 76%p, 검색 요약) [36] (03 §2.3-⑤).
6. **모르면 멈춘다.** 코드에서도, 개발에서도 그렇다. Claude가 확인되지 않은 거래소 API 파라미터를 "아마 이럴 것"이라고 쓰면 그 부분은 PoC로 확인한 뒤에만 쓴다(§2.5).
7. **비밀은 어디에도 두지 않는다.** 클라우드 세션, 코드, 로그, 픽스처, PR 본문, 이슈 모두 해당한다. 클라우드 세션에는 테스트넷 키도 넣지 않는다 [D15][13].
8. **새 패키지는 허용목록 PR로만 들인다.** AI가 지어낸 패키지 이름을 공격자가 먼저 등록해 두는 수법(slopsquatting)을 막는다 [SEC-06].
9. **세션을 역할별로 나눈다.** 외부 글을 읽는 세션과 주문 코드를 쓰는 세션을 분리한다. 외부 글에 숨은 지시문(간접 프롬프트 인젝션)이 코드로 흘러드는 것을 막기 위해서다 [SEC-06] (§1.7).
10. **관문을 건너뛰지 않는다.** G1에서 통과한 규칙이 0개면 3단계 이후 개발을 멈춘다 [Q1+F01]. "거의 통과"는 불통과다.

### 1.3 작업 카드: Claude에게 일을 시키는 법

세션 하나에 카드 한 장만 준다. 끝나면 세션을 닫는다. 대화가 길어지면 앞의 지시를 놓치기 쉽기 때문이다. 카드 전문 양식은 부록 A-1에 있다.

**작성 예시** (1단계, 제안)

```
[작업 카드 1-05] ATR(Wilder 14) 계산
단계: 1 데이터·지표 | 관련 결정: D8(ATR 밴드), D18 | 설계: ARCHITECTURE §2.2 C3
목표: 1H·4H 캔들에서 ATR(Wilder 14, 가격 대비 %)을 계산하는 함수를 만든다.
바꿔도 되는 파일: src/btcbot/features/atr.py, tests/unit/features/test_atr.py,
                 tests/fixtures/candles/btcusdt_1h_sample.csv
하지 말 것: 새 패키지 추가, 네트워크·DB·현재 시각 호출, 다른 폴더 수정
먼저 쓸 테스트:
  - test_워밍업_전에는_ATR값이_없다
  - test_손으로_계산한_예제와_소수_넷째자리까지_같다
  - test_마감되지_않은_봉은_입력에서_빠진다
수용 시험(사용자가 직접): 어제 날짜 BTCUSDT 1H의 ATR(14)을 PR에 표로 붙인다.
  거래소 앱 차트의 ATR(14)과 비교한다(앱의 ATR 계산 방식이 Wilder인지는 확인 필요).
완료 조건: CI 초록, PR 본문에 수용 시험 표와 "처음엔 실패했던 테스트" 목록
참고: Python 3.14, pandas 3.0 기준, 시각은 UTC
```

**카드를 쓸 때 요령**
- 목표는 한 문장으로 쓴다. 두 문장이 필요하면 카드가 두 장이다.
- "하지 말 것"을 꼭 적는다. AI는 친절하게 범위 밖까지 고치는 경향이 있다.
- Claude가 범위 밖 변경을 제안하면 받지 않는다. 새 카드로 적어 둔다.
- 카드 목록은 단계별로 §2에 있다. 카드 번호는 `단계-순번`(예: `1-05`)으로 붙인다(제안).

### 1.4 테스트 먼저: 레드 → 그린

| 순서 | Claude가 하는 일 | 사용자가 확인하는 것 |
|---|---|---|
| 1 | 카드의 "먼저 쓸 테스트"를 작성하고 실행해 **실패**를 확인한다 | PR 본문의 "처음엔 실패했던 테스트" 목록 |
| 2 | 테스트가 통과하도록 최소한으로 구현한다 | CI의 테스트 단계가 초록인지 |
| 3 | 경계값 테스트를 더한다(예: 손익비 정확히 1.5, 손절 정확히 2%) | 테스트 이름에 경계값이 보이는지 |
| 4 | 정리(리팩터링) 후 전체 테스트를 다시 돌린다 | CI 전체 초록 |

- **테스트 이름은 한국어로 써도 된다.** Python 3은 식별자에 한글 같은 비ASCII 글자를 허용한다(PEP 3131, Python 3.0부터) [20][직접]. 예: `test_손절가가_없으면_주문을_거부한다`. 사용자가 CI 로그만 보고도 무엇이 지켜지는지 알 수 있다.
- **이런 PR은 병합하지 않는다**: 테스트를 약하게 고쳐서 통과시켰다 · `assert`가 없는 테스트 · 테스트를 건너뛰기(skip) 처리했다 · 모의 객체가 구현을 그대로 베껴서 무엇을 넣어도 통과한다 · 불변조건 테스트를 지웠다.

### 1.5 PR 단위 검토

PR 본문 양식(부록 A-2)은 `.github/pull_request_template.md`로 저장소에 넣는다(1단계, 제안). 사용자는 폰에서 아래 **다섯 가지만** 확인한다. 1분이면 된다.

| # | 확인 | 아니면 |
|---|---|---|
| 1 | CI가 초록인가 | 병합하지 않는다. "CI를 초록으로 만들어 줘"라고 같은 세션에 요청한다 |
| 2 | 수용 시험 표가 모두 "통과"이고, 내가 직접 해 본 항목이 1개 이상 있는가 | 직접 해 본다 |
| 3 | "보호 경로 변경: 있음"이면 리뷰 기록(`docs/reviews/PR-<번호>.md`)이 있고 "문제 0건"인가 | 리뷰 세션을 연다(부록 A-3) |
| 4 | "새 의존성: 있음"이면 허용목록 PR이 따로 먼저 병합됐는가 | 병합하지 않는다 |
| 5 | "돈 위험 변화"가 "없음"이 아니면, 그 설명을 이해했는가 | Claude에게 "비유로 3줄" 설명을 요청한다 |

- 병합은 **스쿼시 병합**으로 한다. PR 하나가 커밋 하나가 되어 되돌리기가 쉽다(§3.3).
- 이해되지 않는 PR은 병합하지 않는다. "이해 안 됨"은 정당한 거절 사유다.

### 1.6 AI 코드 검토 체크리스트

**A. 사용자용** (코드를 읽지 않고 확인)

- [ ] PR 제목에 카드 ID가 있고, 바뀐 파일이 카드의 "바꿔도 되는 파일" 안에 있다
- [ ] 수용 시험 표, "처음엔 실패했던 테스트" 목록, 되돌리는 법이 모두 있다
- [ ] 삭제된 테스트가 없다. 있으면 이유가 적혀 있다
- [ ] 설정값이 바뀌었다면 **조이는 방향**이다(r 낮추기, 한도 강화, 시나리오 끄기). 완화하는 방향이면 멈추고 §3.2의 절차를 따른다
- [ ] Claude가 대화 중에 "일단 시장가로", "재시도를 넣었다", "키를 환경 변수로", "라이브러리를 하나 추가했다", "테스트가 까다로워서 건너뛰었다" 같은 말을 했다면 그 부분을 되묻는다
- [ ] 백테스트나 페이퍼 결과가 **너무 좋다**(예: 거래당 +1R 이상). 이런 경우 먼저 누수(룩어헤드)를 의심한다 (§6.7)

**B. 리뷰 세션용** (보호 경로 변경 PR은 필수, 나머지는 권장)

| 묶음 | 확인 항목 |
|---|---|
| 범위·구조 | 카드 범위 밖 변경이 없다 · 공용 모듈(★ features·rules·signals·risk·scoring·meta_filter)이 네트워크·DB·현재 시각을 직접 부르지 않는다 · 결정표 값이 코드에 흩어져 있지 않고 설정 또는 코드 상한 상수(①층)에서 온다 |
| 돈 경로 | 모든 주문이 주문 게이트웨이와 방화벽 9항목을 거친다(ARCHITECTURE §2.2 C11) · 청산 주문은 reduceOnly 또는 closePosition이다 · **주문 요청을 자동 재시도하지 않는다.** 응답이 끊기면 주문 ID로 조회부터 한다(I15) · 수량은 내림이고, 최소 명목에 못 미치면 신호를 폐기한다 · 손절 존재 조회에 실패하면 청산하고 T0을 건다(I2) · 설정이 코드 상한보다 느슨하면 시작을 거부한다(I11) · 주문 ID는 `sig-` 접두사와 신호 ID 규칙을 따른다 · 예외가 나면 주문하지 않는 쪽으로 끝난다 |
| 시간·데이터 | 모든 시각이 UTC 시간대 정보가 있는 값이다 · 마감된 봉만 쓴다. 상위 봉도 "마지막으로 마감된 봉"만 쓴다 · 수준(스윙 고저 등)은 확정 시각 이후에만 쓴다 · 지표 워밍업 길이가 백테스트와 실거래에서 같다 [08 §2.7] |
| LLM | `stop_reason`을 먼저 확인한다 · 폴백 모델이 답하면 승인 버튼을 만들지 않는다(I10) · `temperature` 같은 미지원 파라미터와 prefill을 쓰지 않는다(Opus 5.5에서 400 오류) [17] · 프롬프트·스키마 파일을 제자리에서 고치지 않고 새 버전 파일을 만든다 · 프롬프트에 키·잔고·계좌 ID가 없다 · 확신도·수준 ID 범위를 코드가 검증한다(구조화 출력은 숫자 범위를 강제하지 않는다) [15] |
| 텔레그램 | 숫자 사용자 ID와 private 채팅 ID를 모두 확인한다 · 버튼 데이터 형식이 `v1:동작:랜덤신호ID`다 · 상태 전이가 원자적이다(I9) · Claude 텍스트는 평문으로 보내고 URL을 지운다 · 가격·수량은 DB 값만 보여 준다(I16) · 텔레그램으로 한도 완화·정지 해제가 불가능하다(I14) |
| 비밀·보안 | 비밀이 코드·로그·픽스처·PR 본문에 없다 · 비밀은 파일에서만 읽는다(환경 변수 금지) · HTTP 디버그 로그가 꺼져 있다(텔레그램 토큰이 URL에 들어간다) · SQL은 매개변수 바인딩을 쓴다(문자열로 조립하지 않는다) |
| AI 특유 실수 | 존재하지 않는 패키지·함수·API 파라미터가 없다. 특히 ccxt의 바이낸스 algo 주문 파라미터는 PoC 결과(`docs/poc/`)나 바이낸스 공식 SDK [32]로 확인했다 · pandas 2 시절 방식(체인 할당 등)이 없다. pandas 3.0은 Copy-on-Write가 기본값이다 [21] · 예외를 조용히 삼키는 코드(`except: pass`)가 없다 · 핵심 로직이 TODO로 남아 있지 않다 · 테스트를 약하게 바꿔 통과시키지 않았다 |
| 공급망·CI | 새 의존성이 없다(또는 별도 허용목록 PR) · `uv.lock` 변경이 의도한 것뿐이다 · 워크플로 권한이 최소(`contents: read`)다 · 외부 Action은 전체 커밋 SHA로 고정했다 · `pull_request_target`을 쓰지 않는다 [secure-use 문서: 29] |

**C. 리뷰 세션 지시문**은 부록 A-3에 있다. 리뷰 결과의 형식은 "항목 | 통과/문제/해당 없음 | 근거(파일:줄)"이다.

### 1.7 세션 분리와 권한

INFRA §1.2의 규칙을 개발 절차로 옮긴 것이다 [SEC-06(5)].

| 세션 | 네트워크 수준 | WebFetch | 쓰는 곳 | 여는 방법 (제안) |
|---|---|---|---|---|
| 조사 | Trusted 또는 Custom | 허용 | `research/`만 | 별도 클라우드 환경. 브랜치 이름 `research/<주제>` |
| 코드 작성 | Trusted (패키지 저장소·GitHub) | **주지 않는다** | 카드 범위 | 코드용 클라우드 환경. 외부 문서가 필요하면 조사 세션에 맡기고 결과 문서만 읽힌다 |
| 리뷰 | Trusted | 주지 않는다 | `docs/reviews/`만 | 작성 세션을 닫고 새 세션을 연다 |

- 클라우드 세션의 네트워크 수준은 None / Trusted / Custom / Full이 있다. 환경 변수는 그 환경을 쓰는 누구나 읽을 수 있다 [13](05 §2.13.1).
- 지금 저장소의 `.claude/agents/`에는 리서치 에이전트 5개가 있다. 그중 3개(chartpro-researcher, wonyotti-researcher, research-verifier)는 Bash·Write·WebFetch 권한을 모두 가진다[직접]. 이 에이전트들은 **조사 세션에서만** 부른다. 코드 작성 세션에서는 부르지 않는다.
- **강제 방법**: CI가 PR마다 "조사 PR은 `research/`·`docs/`만 바꾼다, 코드 PR은 `research/`를 건드리지 않는다"를 검사한다(제안, §3.5). 도구 사용 자체를 막아야 하면 Claude Code의 PreToolUse hook을 쓸 수 있다 [12]. 이것은 "나중"으로 둔다.

### 1.8 CLAUDE.md와 `.claude/rules/` 활용

- **CLAUDE.md**는 모든 세션이 시작할 때 읽는 프로젝트 지침 파일이다. `./CLAUDE.md` 또는 `./.claude/CLAUDE.md`에 둔다. 공식 문서는 200줄 이하로 쓰라고 권한다 [12][직접]. 초안 목차는 부록 B에 있다. 1단계 첫 PR에서 만든다(제안).
- **`.claude/rules/`**에는 폴더별 규칙을 둔다. `paths` 항목을 달면 그 경로의 파일을 다룰 때만 규칙이 적용된다 [12][직접]. 예: `.claude/rules/execution.md`(paths: `src/btcbot/execution/**`, `src/btcbot/risk/**`)에 주문 경로 규칙(§4.6)을 둔다.
- **한계**: 두 파일 모두 "지침"이지 "강제"가 아니다 [12]. Claude가 어겨도 막히지 않는다. 그래서 같은 규칙을 **CI 검사와 불변조건 테스트로 한 번 더** 강제한다. 지침만 믿지 않는다.
- Claude가 같은 실수를 두 번 하면 CLAUDE.md에 한 줄 추가한다. 공식 문서도 이 시점을 추가 시점으로 권한다 [12].

### 1.9 이럴 땐 멈춘다

| 신호 | 왜 위험한가 | 할 일 |
|---|---|---|
| Claude가 "CI를 잠시 끄자", "강제 푸시(force push)하자"고 한다 | 검사 우회 | 거절한다 |
| Claude가 보호 경로를 "조금만" 고쳤다고 한다 | 돈 경로 변경 | 리뷰 세션을 연다 |
| 같은 오류를 세 번 고쳐도 계속 난다 | 원인을 모른 채 덧대고 있다 | 세션을 닫고 새 세션에서 "원인 분석만" 카드로 다시 시작한다 |
| 백테스트 결과가 매우 좋다 | 룩어헤드·비용 누락일 가능성이 크다 [08 §2.7] | §6.7 체크리스트를 먼저 돈다 |
| 거래소 API 설명이 조사 문서와 다르다 | API 변경 가능성. 2025-12-09에 손절 주문 창구가 바뀐 전례가 있다 [33] | PoC로 확인한다 |
| 테스트넷·페이퍼에서 손절 없는 포지션이 한 번이라도 보인다 | 최상위 불변조건 위반 | 해당 단계를 멈추고 원인을 찾는다 (§2.5) |

- **돌아가기**: 어느 단계에서든 규칙 파라미터를 바꾸면 G1부터 다시 한다(새 명세 버전). 모델·프롬프트·스키마를 바꾸면 D21 절차(섀도 병행 쌍 비교)를 따르고, 코드 규칙 트랙(G1, G4 성과)은 리셋하지 않는다 [D21].
- **범위 관리**: "실거래 전 필수 / 나중 / 안 함" 표(PLAN §7.3)에 없는 기능은 카드로 만들지 않는다 [F03]. "나중" 항목은 G4 이후에 카드를 만든다.
- **신호만 받고 수동 주문**: 3단계가 사실상 이 형태다. 하지만 G1·G3를 통과하기 전에 이 신호로 실제 돈을 수동 매매하지 않는다. 사람이 손절을 잊을 위험도 있다 (PLAN §7.1).

### 3.3 브랜치·커밋·태그 규칙

| 항목 | 규칙 |
|---|---|
| `main` | 언제나 배포 가능한 상태. 직접 푸시하지 않는다. PR로만 들어간다 |
| 작업 브랜치 | 카드 1장 = 브랜치 1개. Claude Code 클라우드 세션은 `claude/...` 브랜치를 스스로 만든다(이 저장소의 현재 브랜치도 `claude/funny-bell-8fkiag`다)[직접]. 직접 만들 때는 `s<단계>/<주제>`(예: `s1/atr-wilder`)(제안). 병합 뒤 삭제한다 |
| 조사 브랜치 | `research/<주제>`. `research/`·`docs/`만 바꾼다 |
| 장기 브랜치 | 두지 않는다(`develop` 없음). 혼자 개발하므로 단순하게 간다 |
| 병합 방식 | 스쿼시 병합 |
| 커밋 메시지 | 한국어 한 줄 + 카드 ID. 예: `[1-05] ATR(Wilder 14) 계산 추가` |
| 되돌리기 | `git revert`를 새 PR로 올린다. 강제 푸시로 이력을 지우지 않는다 |
| 태그 | `vMAJOR.MINOR.PATCH`. CI가 초록인 `main` 커밋에만 붙인다. 단계·기능 추가는 MINOR, 수정은 PATCH, 실거래 시작은 `v1.0.0`(제안) |
| 배포 | 태그만 배포한다. `deploy.sh <태그>` 한 번으로 끝낸다 (INFRA §5) |
| 긴급 수정 | 같은 절차를 빠르게 밟는다. 안전 상태 확인을 건너뛰는 `--force`는 긴급 수정에만 쓴다 (INFRA §10.7) |

### 3.4 GitHub 설정과 요금제 제약 — **[결정 필요]**

**사실** (모두 GitHub 공식 문서 원문, [직접])

| 기능 | 무료 개인 계정 · 비공개 저장소 | GitHub Pro · 비공개 저장소 | 출처 |
|---|---|---|---|
| 브랜치 보호(병합 전 CI 통과 강제 등) | ✕ (공개 저장소만) | ○ | [2] |
| 룰셋 | ✕ (공개 저장소만) | ○ | [4] |
| CODEOWNERS | ✕ (공개 저장소만) | ○ | [3] |
| GitHub 비밀 스캐닝·push protection | ✕ | ✕ (사용자 소유 비공개 저장소에는 제공 안 됨) | [5] |
| Actions 무료 시간 | 월 2,000분 | 월 3,000분 | [8] |

- 결제 수단을 등록하지 않으면 무료 시간을 다 쓴 뒤 Actions가 **멈춘다.** 몰래 요금이 나가지 않는다 [8][직접].
- 브랜치 보호의 "Require review from Code Owners"를 켜면 코드 소유자가 승인해야 병합된다. 관리자는 기본적으로 보호 규칙을 우회할 수 있고, "Do not allow bypassing the above settings"를 켜야 관리자에게도 적용된다 [6][직접].
- PR 작성자 본인이 자기 PR을 승인할 수 있는지, 그리고 Claude Code 클라우드 세션이 만든 PR의 작성자가 누구로 기록되는지는 **확인 필요**다. 둘 다 "승인 필수" 설정이 혼자 개발하는 저장소에서 병합을 막을지 좌우한다.

**선택지**

| 선택 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **(a) GitHub Pro 구독** | 비공개 저장소에서 브랜치 보호·CODEOWNERS·룰셋을 쓴다 | "CI가 초록이 아니면 병합 불가"를 GitHub가 기계적으로 강제한다 | 월 요금(**확인 필요**). 비밀 스캐닝은 여전히 없다 |
| **(b) 무료 유지 + 보완 통제** | 아래 세 가지로 대신한다 | 비용 0 | 병합 전 강제가 없다. 사용자 규율에 기댄다 |

(b)의 보완 통제 (제안)
1. **배포 시점 재검사**: `deploy.sh`가 서버에서 이미지를 만든 뒤 컨테이너 안에서 전체 테스트와 gitleaks를 다시 돌린다. 실패하면 배포하지 않는다. 병합은 막지 못해도 **실행은 막는다.**
2. **보호 경로 검사**: CI가 보호 경로 변경과 리뷰 기록 유무를 검사해 빨간 X를 띄운다.
3. **사용자 규칙**: "빨간 X가 있는 PR은 병합하지 않는다. 태그는 초록 커밋에만 붙인다."

**추천**: 요금을 확인한 뒤 부담이 없으면 **(a)**를 권한다. 코드를 읽지 못하는 사용자에게는 "사람의 주의"보다 "기계의 차단"이 낫다. (a)를 골라도 (b)의 1번(배포 시점 재검사)은 함께 둔다(이중 방어).

**어느 쪽이든 켜 둘 것**
- Actions의 기본 `GITHUB_TOKEN` 권한을 읽기 전용으로 둔다. 공식 문서가 권하는 설정이다 [29][직접].
- 외부 Action은 **전체 커밋 SHA로 고정**한다. 공식 문서는 이것이 Action을 변경 불가능하게 쓰는 유일한 방법이라고 적는다 [29][직접].
- `pull_request_target` 트리거는 쓰지 않는다 [29][직접].
- CI에는 어떤 비밀도 넣지 않는다. gitleaks-action은 개인 계정이면 라이선스 키 없이 `GITHUB_TOKEN`만으로 돈다 [10][직접].

- pip-audit를 uv 프로젝트에 어떻게 붙일지(환경 검사 또는 내보낸 목록 검사)는 1단계에서 정한다(**확인 필요**).
- `uv.lock`에 파일 해시가 기록되는지는 06 문서가 확인 필요로 남겼다. 1단계 PoC(카드 1-15)에서 `uv.lock`을 열어 해시 항목을 확인한다.

- 백테스트 환경(freqtrade 등)은 운영 CI와 분리한다. 별도 허용목록을 둔다(제안).

## 4. 코딩 규칙

Claude에게 코드를 요청할 때 CLAUDE.md와 작업 카드로 이 규칙을 알려 준다. 중요한 규칙은 테스트·CI로도 강제한다(표의 "강제" 열).

### 4.1 언어·도구

| 규칙 | 강제 |
|---|---|
| Python 3.14 (`.python-version`). 3.14는 버그 수정이 2027-10까지, 보안 수정이 2030-10까지다 [22] | uv가 버전 고정 |
| 패키지는 uv로만 관리한다. `pip install` 금지 | CI `uv sync --locked` |
| 외부 패키지는 결정표 D9 목록뿐이다: ccxt 4.5.x(고정), pandas 3.0.x, anthropic 1.x, python-telegram-bot 22.8[job-queue], pydantic-settings, matplotlib(mplfinance는 pandas 3 호환 확인 뒤에만) + 개발 도구 pytest, ruff, gitleaks, pip-audit | CI 허용목록 |
| **pandas 3.0 기준**으로 쓴다. 문자열 전용 타입이 기본이고, Copy-on-Write가 기본이며, 날짜 해상도를 입력에 맞춰 추론한다 [21]. 옛 예제의 체인 할당(`df[...][...] = 값`)을 쓰지 않는다 | 리뷰, 경고를 오류로 처리하는 테스트 설정(제안) |
| 지표는 pandas로 직접 계산한다. 지표 라이브러리를 쓰지 않는다 | 허용목록 |

### 4.2 구조

- **공용 모듈(★)은 순수 함수**다: `features/`, `rules/`, `signals/`(전이 규칙), `risk/`, `scoring/`, `rules/meta_filter/`. 네트워크·DB·현재 시각을 직접 부르지 않는다. 같은 입력이면 같은 출력이다. 백테스트·페이퍼·실거래가 이 코드를 **그대로** 쓴다 [Q6][Q8].
- 현재 시각이 필요하면 인자로 받는다(시계 주입). 그래야 가짜 시계로 만료·일일 경계를 시험할 수 있다.
- 입출력(네트워크·DB·파일)은 가장자리에만 둔다: `apps/`, `storage/`, `data/`, `notify/`, `execution/adapters/`.
- 시나리오 하나당 파일 하나, 파일 맨 위에 규칙 버전을 적는다 (ARCHITECTURE C4).

### 4.3 시간·데이터

- 내부 시각은 **UTC, 시간대 정보가 있는 값**만 쓴다. 시간대 없는 날짜(naive datetime)는 금지다. 화면·텔레그램 표시만 KST로 바꾼다 (D1).
- 봉은 "UTC 시작 시각(밀리초) + 타임프레임"으로 식별한다.
- **마감된 봉만** 쓴다. 마감 여부는 거래소 서버 시각으로 판정한다. 받은 목록의 마지막 봉이 아직 안 끝났으면 버린다 (ARCHITECTURE C2).
- 상위 봉(4H·일봉)도 **마지막으로 마감된 봉**만 쓴다 [08 §2.7-2].
- 스윙 고저처럼 나중에 확정되는 수준은 **확정 시각 이후**에만 쓴다 [08 §2.7-3].
- 지표 워밍업 길이는 백테스트와 실거래가 같다 [08 §2.7-4].
- 하루 경계는 UTC 00:00(= KST 09:00)이다 (D8).
- 데이터는 **USDⓈ-M 무기한 선물** 것만 쓴다. 현물 캔들을 섞지 않는다 [Q16].

### 4.4 숫자·가격·수량

- 가격·수량은 거래소 정밀도 규칙에 맞춰 자른다. **수량은 항상 내림**한다. 올림하면 위험이 r을 넘을 수 있다 (ARCHITECTURE C6).
- 수량 = (R 자본 × r) ÷ (|E − S| + 비용). 그다음 명목 ≤ R 자본 × 0.6과 코드 상수 절대 상한을 검사한다. 최소 주문 명목에 못 미치면 신호를 폐기한다 (D8, ARCHITECTURE C6).
- 모든 % 한도는 **R 자본**(설정 상수, 서버에서 사람이 갱신) 기준이다. 서브계정 잔고를 기준으로 쓰지 않는다 [Q10].
- 손익비는 **비용 차감 후, 계획 평균 진입가와 단일 목표가 기준**으로 계산한다. 목표가 선택 규칙은 `RULES_SPEC.md`에 미리 고정한다("목표가 쇼핑" 방지) [Q6+F11+Q12].
- 변수 이름에 단위를 붙인다: `_pct`(%), `_ratio`(0~1), `_usdt`, `_r`(R배수), `_ms`(밀리초)(제안). %와 비율을 섞는 실수를 막는다.
- 소수 비교는 허용 오차로 한다. 경계값(1.5, 2%, 0.4%)은 테스트로 고정한다.

### 4.5 오류 처리와 fail-closed

- 예외를 조용히 삼키지 않는다(`except: pass` 금지). 잡았으면 기록하고, 신규 진입을 막는 쪽으로 끝낸다.
- 거래소 오류는 내부 코드로 정규화한다: `REGION_BLOCKED`(451/403), `RATE_LIMIT`(429), `IP_BANNED`(418), `CLOCK_SKEW`(-1021), `ORDER_TYPE_UNSUPPORTED`(-4120) 등 (ARCHITECTURE C12).
- 조회는 간격을 늘려 가며 제한된 횟수만 재시도한다. **주문 요청은 재시도하지 않는다**(I15). 응답이 끊기면 주문 ID로 조회해 있음/없음을 확정한다. 확정 전에는 두 번째 주문을 내지 않는다 (ARCHITECTURE §6.2-2).
- 상태가 불확실하면 T0(신규 차단)을 건다. **기존 손절은 지우지 않는다** (ARCHITECTURE §6.1).

### 4.6 주문 경로 전용 규칙 (`.claude/rules/execution.md`에도 둔다)

1. 주문은 주문 게이트웨이의 공개 함수로만 낸다. 어댑터를 다른 곳에서 직접 부르지 않는다.
2. 방화벽 9항목(ARCHITECTURE C11)을 모든 주문에 적용한다.
3. 코드 상한(①층)은 설정으로 **낮출 수만** 있다. 설정이 더 느슨하면 시작을 거부한다(I11).
4. 주문 ID는 `sig-<신호ID>-<용도>` 형식이다(예: `-e1` 진입). 한 신호에 진입 주문은 한 번뿐이다(I6).
5. 청산 주문은 반드시 reduceOnly 또는 closePosition이다(I7). 손절은 algo STOP_MARKET(closePosition=true, workingType=MARK_PRICE, priceProtect=false, clientAlgoId=신호ID)이다 (D7).
6. 순수 시장가 진입은 쓰지 않는다. 진입 방식은 PoC C1 결과에 따른다 (D7).
7. 진입 체결 뒤 정해진 시간(제안 5초) 안에 손절이 **조회로** 확인돼야 한다. 아니면 즉시 reduceOnly 시장가로 청산하고 T0을 건다(I2).
8. `countdownCancelAll`은 algo 손절까지 지우는지 확인(C2)하기 전에는 쓰지 않는다 (08 §3.1).
9. PAPER 모드 프로세스는 거래소 개인키 파일을 열지 않는다(I12).

### 4.7 LLM(Claude) 호출 규칙

1. Claude에게 도구(주문·웹)를 주지 않는다. Claude는 JSON만 낸다 (01 §3.2-4).
2. 형식은 구조화 출력(`output_config.format` JSON 스키마)으로 강제한다. assistant prefill은 쓸 수 없다 [15][17].
3. 응답을 읽기 전에 `stop_reason`부터 본다. `end_turn`이 아니면 "분석 실패"로 기록하고 알림·버튼을 만들지 않는다 [16].
4. 응답의 실제 모델 ID를 매번 저장한다. 폴백 모델이 답했으면 기록만 하고 버튼을 만들지 않는다 (D2, SEC-11).
5. `temperature`·`top_p`·`top_k`를 기본값 외로 주지 않는다. Opus 5.5에서 400 오류가 난다. 공식 문서는 temperature 0도 같은 출력을 보장한 적이 없다고 적는다 [17]. 재현성은 설정이 아니라 **로그**(입력 스냅샷 + 원본 응답)로 확보한다 (03 §2.3-②).
6. "추론 과정을 모두 적어라" 같은 지시를 넣지 않는다. `reasoning_extraction` 거절을 부를 수 있다 [19]. 근거는 짧게(3개 이내, 한 문장씩) 받는다.
7. 가격을 Claude가 쓰지 않는다. 코드가 준 수준 ID를 enum으로 고르게 한다 (D3).
8. 구조화 출력은 숫자 범위(min/max)를 강제하지 않는다. 확신도 0~1, 수준 ID 소속 같은 범위는 **코드가 검증**한다 [15].
9. 실패하면 1회만 다시 부른다. 답이 마음에 안 든다고 다시 묻지 않는다(답 고르기 = 체리피킹) (03 §2.3-②).
10. 프롬프트에 거래소 키, 계좌 ID, 잔고, 개인정보를 넣지 않는다 (03 §2.5.7).
11. 프롬프트·스키마 파일은 제자리에서 고치지 않는다. `system_v2.md`처럼 새 버전 파일을 만든다(§7.8).

### 4.8 텔레그램 규칙

- `callback_data`는 `v1:동작:랜덤신호ID`(ASCII, 64바이트 이하)만 넣는다. 가격·수량은 DB에서 다시 꺼낸다. 버튼 데이터는 사용자 앱이 보내는 값이라 조작될 수 있다 [07 §2.3] (D5).
- 검사 순서: answerCallbackQuery → 숫자 사용자 ID → 채팅 ID(private만) → 형식 → DB 상태 → 킬 스위치·한도 → 가격 재검증 (07 §3.2).
- Claude 텍스트는 서식 해석 없이 평문으로 보내고, URL을 지우고, 링크 미리보기를 끄고, 길이를 제한한다 [SEC-11].
- 재시작할 때 밀린 업데이트를 버리지 않는다(`drop_pending_updates=False`) (07 §3.2).
- 텔레그램으로는 어떤 한도도 완화하지 못하고 정지도 풀지 못한다(I14).

### 4.9 설정·비밀

- 설정은 pydantic-settings로 형식을 검증한다. 비밀 필드는 **비밀 파일에서만** 읽도록 설정 소스를 좁힌다. pydantic-settings의 기본 우선순위는 환경 변수가 비밀 파일보다 앞이라, 그대로 두면 떠돌던 환경 변수가 비밀을 덮을 수 있다 (ARCHITECTURE C20).
- 비밀은 Compose secrets 파일(`/run/secrets/<이름>`)로 받는다. 환경 변수는 모든 프로세스에 보이고 로그에 찍힐 수 있어 쓰지 않는다 [30] (D15).
- 저장소의 `config/`에는 비밀·계정 ID·채팅 ID를 넣지 않는다. 그런 값은 서버의 `site.toml`(저장소 밖)에 둔다 (ARCHITECTURE §7.1).

### 4.10 로그·감사

- 진단 로그는 내장 logging을 쓴다. 감사 기록은 로그 파일이 아니라 DB의 `audit_log`(추가 전용)에 남긴다 (06 §2.3.8).
- 로그에 비밀·토큰을 찍지 않는다. HTTP 라이브러리의 디버그 로그를 끈다. 텔레그램 봇 토큰은 URL 경로에 들어가서 디버그 로그에 그대로 찍힌다 (D15).
- 주문·전이·설정 변경·배포는 모두 감사 로그에 남긴다.

### 4.11 이름·주석

- 코드 식별자는 영어로 쓴다. **테스트 이름은 한국어**로 쓴다(§1.4) [20].
- 모듈 맨 위에 한국어 설명 3줄을 둔다: 무엇을 하나, 왜 필요한가, 관련 결정표 ID·설계 절(제안). 사용자가 파일 목록만 보고도 역할을 알 수 있다.
- 설정값 옆에는 결정표 ID 주석을 단다(예: `# D8`).

  - Claude 응답: 정상, 거절, `max_tokens` 잘림, 폴백 모델 응답, 스키마 위반
  - 텔레그램 업데이트: 정상 클릭, 같은 업데이트 재수신, 다른 사용자, 오래된 `/stop`
- 픽스처는 서버나 집 PC에서 녹화한다. 저장 전에 키·토큰·계정 UID·채팅 ID를 지운다. gitleaks가 픽스처도 검사한다.
- 파일 하나는 5MB 이하로 둔다(제안). 큰 과거 데이터는 저장소에 넣지 않고 백테스트 환경에서 받는다.
- DB는 테스트마다 임시 SQLite 파일을 만든다. 시각은 가짜 시계로 준다.

### 5.5 재생 동등성 테스트

- **왜**: 백테스트 코드와 실시간 코드가 조금이라도 다르면 G1 결과가 실거래를 대표하지 못한다 [Q6][Q8].

- 공용 모듈(★)이 바뀌는 모든 PR에서 돈다.

### 5.7 테스트넷 (G2)

- 순서: PoC(§2.5) → 불변조건 테스트 → 구현 → staging 배포 → 16개 시나리오.
- 테스트넷·데모의 호가와 체결은 실거래와 다를 수 있다 (08 §3.4-7). 그래서 G2는 **동작 점검**이지 성과 판단이 아니다. 우위가 없는 전략도 20건에서는 40% 확률로 이익처럼 보인다 (08 §2.9).
- ccxt를 올릴 때마다 staging에서 "진입 → 손절 존재 → 청산" 회귀 시험을 다시 한다 (04 §3.3-5).

### 5.8 페이퍼 (G3)

- 모든 신호를 기록하고 채점한다: 승인·패스·만료·차단·Claude 실패 신호 모두 (§7.3).
- 사람이 버튼을 누르기까지 걸린 시간을 모은다. 이 분포가 체결 모델의 지연 L을 대체한다 (ARCHITECTURE C14).
- 주간 리포트(§7.11)를 매주 만든다.
- 판정은 사전 등록한 방식으로만 한다. 중간에 방식을 바꾸지 않는다.

### 5.9 CI 게이트와 품질 기준

- 모든 층의 테스트가 100% 통과해야 한다. 실패를 "알려진 문제"로 남겨 두지 않는다.

## 6. 백테스트 방법론

### 6.1 원칙

1. **코드 규칙만 백테스트한다.** Claude가 들어간 판단은 과거 백테스트를 하지 않는다. Opus 5.5의 학습 데이터는 2026-06까지라 과거 결과를 "기억"한다 [18]. 가리기나 "모른다고 가정하라" 같은 지시로도 제거되지 않았다는 연구가 있다(검색 요약) [37] (03 §2.3-④).
2. **먼저 고정하고 나중에 본다.** 규칙, 변형, 판정 기준을 백테스트 전에 문서로 고정한다 [Q1+F01].
3. **백테스트·페이퍼·실거래가 같은 코드를 쓴다.** 공용 모듈과 공용 체결 모델 [Q6][Q8].
4. **보수적으로 가정한다.** 지정가는 관통해야 체결, 같은 봉 손절·익절은 손절, 비용 2배 시험.
5. **시도한 모든 것을 기록한다.** 실패한 변형도 지우지 않는다 [Q14].

### 6.5 체결·채점 모델 (공용, v1)

G1 백테스트, G3 페이퍼, 패스·만료·차단 신호의 사후 채점이 **모두 이 모델**을 쓴다 [Q6+F11+Q12] (D18, ARCHITECTURE C14).

| 항목 | 규칙 |
|---|---|
| 진입 시각 | 신호 시각 + 지연 L. G1에서는 L = 3분·8분·15분 세 가지로 민감도를 본다(가정). G3부터는 실측한 클릭 시간 분포를 쓴다 |
| 대기형 지정가 | 계획가에 걸고, 가격이 계획가를 **관통해야** 체결로 본다. 닿기만 하면 미체결. GTD가 만료되면 미체결로 따로 센다 |
| IOC 상한 (L1b 등) | L 시점 가격이 상한 안일 때만 체결 |
| 손절·익절 | 한 봉에서 둘 다 닿으면 1분봉으로 순서를 확인한다. 확인할 수 없으면 **손절**로 친다 [08 §2.7-5] |
| 시간 제한 | 두지 않는다. 72시간을 넘긴 건은 "장기 미결"로 표시만 한다. 시간 손절(48시간 후보)은 비교 항목이다 |
| 부분 체결 | v1은 전량 체결 또는 미체결로 단순화한다(제안). 실제 부분 체결 비율은 G4에서 잰다 |
| 손익비 | 계획 평균 진입가와 단일 목표가 기준, 비용 차감 후 ≥ 1.5 |
| 결과 단위 | R배수(비용 포함). 승/패가 아니라 R로 적는다 |

**왜 이렇게 까다롭게 하나**: 승인 지연 15분 동안 가격 표준편차는 약 0.24%다(추정). 손절 거리가 1H ATR 중앙값 0.57%이면, 괴리 한도 min(0.25×손절 거리, 0.3%)를 넘을 확률이 약 55%다(정규 근사) [Q6]. freqtrade 기본 가정("다음 봉 시가 진입, 범위 안이면 슬리피지 없이 체결")을 그대로 쓰면 성과가 부풀려진다 [23].

### 6.6 비용: 수수료·펀딩·슬리피지

| 비용 | 기본값 | 근거 |
|---|---|---|
| 테이커 수수료 | 0.05% | 바이낸스 USDⓈ-M 기본 등급(검색 요약. 가입 전 공식 수수료 페이지 확인 필요) (08 §2.4) |
| 메이커 수수료 | 0.02% | 같음 |
| 슬리피지 | 시장가·손절에 0.05% (가정) | 평상시 0.02~0.05%로 가정했다. 공식 수치 없음 (08 §2.4-2). 급변일에는 더 나쁠 수 있다. 1시간봉 최대 하락이 −24.5%인 날도 있었다 [34][계산] |
| 펀딩비 | 보유 기간 동안의 **실제 값** | 명목 600 USDT를 24시간 들면 0.01% 기준 약 0.015R로 작지만, 보유 시간과 함께 넣는다 (08 §2.4-3) |
| 민감도 | **비용 2배**로 다시 돌린다 | D17-(1) 조건 |

- 손절이 좁을수록 비용이 우위를 먹는다. 손절 0.5%에 시장가 위주면 손익분기 승률이 52%다 (08 §2.4-4). ATR 밴드 하한이 필요한 이유다.
- 손익비 1.5에서 무작위로 들어가도 승률은 약 39~40%다 (08 §2.1-3). 우리 신호는 이 기준선을 **비용까지 넘어서야** 한다.

### 6.7 룩어헤드(미래 정보 누수) 방지 체크리스트

| # | 점검 | 방법 |
|---|---|---|
| 1 | 마감 안 된 봉을 쓰지 않았다 | 구조(§4.3) + 단위 테스트 + freqtrade `lookahead-analysis` [24] |
| 2 | 상위 봉도 마지막으로 마감된 봉만 썼다 | 단위 테스트 |

| 5 | 같은 봉 손절·익절은 보수적으로 처리했다 | 체결 모델 |
| 6 | 지정가 체결을 관통 기준으로 했다 | 체결 모델 |

- **주의**: `lookahead-analysis`는 발동하지 않은 신호를 검증하지 못한다는 한계가 있다 (08 §2.7-1). 또 통계 검정은 누수를 잡지 못한다. 미래 정보를 일부러 흘린 "오라클" 전략이 DSR·PBO 검정을 통과했다는 보고가 있다(검색 요약) (08 §2.8). **구조적 차단이 먼저**다.

- **무엇**: "그 시각에 사람이 실제로 승인할 수 있었나"를 표시한다 [Q5+F08].
- **구성**: 방해 금지(기본 00:30~07:30 KST), 사용자 응답 가능 시간표(PLAN §11 #7 답변), 하루 승인 요청 6건 상한, 동시 1포지션, `/away` 기간.
- **보고**: 결과를 "전체 신호"와 "실행 가능 신호"로 나누고, 시간대별(낮 07:30~18:00 / 저녁 18:00~00:30 / 심야 00:30~07:30 KST, 제안)로도 나눈다 (ARCHITECTURE C14).
- **왜 중요한가**: 2025-01 이후 거래량이 직전 20봉 평균의 3배 이상인 1시간봉 592개 중 **34.0%가 00:30~07:30 KST에 마감**했다. 42.7%는 22~01시 KST에 시작했고, 09~18시에 마감한 봉은 23.8%였다 [34][계산, 검토 단계 재현] [Q5]. 기준봉 시나리오는 한국 심야에 몰리므로, 마스크를 빼면 실제로는 못 탈 신호로 성과를 계산하게 된다.
- G1 기대값 조건은 **실행 가능 신호** 기준이다 (D17-(1)).

### 6.9 표본 구분: 무엇이 "표본 밖"인가

| 구간 | 성격 | 쓰임 |
|---|---|---|
| 2026-09 이전 전체 | **표본 안(in-sample)** | ATR 밴드·손절 소음 표를 만드는 데 이미 쓰였다(2024-01~2026-09) [Q2] (D18) |
| 그 안의 워크포워드 검증 구간 | 창 기준 표본 밖 | 각 창에서 학습에 쓰지 않은 구간. **G1의 "표본 밖 기대값"은 이 구간 결과를 이어 붙여 계산한다**(해석, 제안). 위 파라미터 선정 때문에 약하게 오염돼 있음을 보고서에 적는다 |
| 규칙 고정일 이후 (A6 전향 기록) | **진짜 홀드아웃** | 1단계부터 24시간 쌓는다. G1 시점에는 짧아서 판정에 쓰지 않는다. G3 동안 함께 쌓아 "G1 예측 범위 안인지" 확인한다(제안) [A6] |

- 08 문서가 홀드아웃으로 잡았던 2026-04~09는 더 이상 별도 홀드아웃이 아니다 [Q2]. 이 구간을 워크포워드 검증 구간에 넣을지는 `RULES_SPEC.md`에서 미리 정한다(제안).
- 한 번 본 전향 구간으로 규칙을 다시 조정하지 않는다. 재설계하면 새 고정일부터 새 전향 구간이 시작된다.

### 6.10 워크포워드 설계

- **기본안** (08 §2.8-4): 학습 12개월 → 검증 3개월, 3개월씩 이동. 검증 구간 2023-01~2026-03, 13개 창.
- 각 창에서 학습 구간 1등 변형을 **검증 구간에 그대로** 적용한다. 검증 구간 결과만 이어 붙여 평가한다.
- **창당 예상 거래 수를 먼저 추정한다.** 30건 미만이면 "창별 양수 비율" 대신 표본 밖 결과를 합쳐 순열 검정을 한다 [Q14].
- 진단 지표(관문이 아니라 보고용): 1등 변형 주변(파라미터 ±20%)도 양수인지(뾰족한 1등이면 의심), 워크포워드 효율(검증 성과 ÷ 학습 성과, 관행 기준 ≥ 0.5), 연도·국면별(하락 2022, 상승 2023~24, 횡보·하락 2025~26) 성과 (08 §2.7-11, §2.10).

### 6.11 기준선 (벤치마크)

| 기준선 | 내용 | 쓰임 |
|---|---|---|

### 6.12 과최적화 방지

| 장치 | 내용 |
|---|---|
| 변형 제한 | 1차 G1은 L1a/L1b, S2, S3 + 방향 필터 1~2종 + 1H/4H 비교로 좁힌다 [Q14] (D18) |
| 시도 수 기록 | 레지스트리의 모든 시도를 DSR·PBO에 넣는다. 변형 16개만으로도 하나가 우연히 "유의"할 확률이 56%다 (08 §2.8-1) |
| DSR | 시도 횟수를 반영해 샤프를 깎는다. 최종 후보 보고에 함께 적는다 [27] |

| 재조정 금지 | 검증·전향 구간을 본 뒤 파라미터를 바꾸면 그 구간은 더 이상 표본 밖이 아니다 |

| 수집만 | OI·롱숏비는 6개월 이상 쌓이기 전에는 관문에 쓰지 않는다 [Q16] |

DSR·PBO 계산 도구는 백테스트 환경에서 직접 구현하거나, 새 패키지 도입 체크리스트(06 §3.3)를 통과한 라이브러리를 백테스트 전용 허용목록에 넣어 쓴다(제안). pypbo의 유지보수 상태는 **확인 필요**다.

### 6.13 1H vs 4H 비교

- 같은 리스크 규칙으로, **지연·가용성을 반영한 뒤**의 성과로 비교한다 (D1).
- 성과가 비슷하면 설정 2(4H)를 기본으로 한다 (D1). 4H는 승인 지연 피해가 1H의 절반 이하이고 알림 피로가 적다 [A2].
- "비슷함"의 정의(제안): 두 설정의 실행 가능 신호 평균 R 차이의 부트스트랩 95% 구간이 0을 포함하면 비슷하다고 본다. `RULES_SPEC.md`에 미리 적는다.
- ATR은 신호 봉 기준이다. 4H 설정이면 4H ATR로 다시 계산한다 (D8).

### 6.14 통계 방법 (쉬운 설명)

| 지표 | 뜻 | 기준 |
|---|---|---|
| 평균 R (기대값) | 거래 1건당 평균 손익 | D17-(1): ≥ +0.15R |
| 부트스트랩 95% 구간 | 거래 결과를 다시 뽑기를 반복해 평균의 불확실성을 잰다. 거래 단위와 월 단위 블록 두 방식으로 계산해 병기한다(제안. 연속된 거래끼리 비슷할 수 있어서) | 하한 > 0 |
| PF | 이긴 거래 이익 합 ÷ 진 거래 손실 합 | ≥ 1.2 |
| 순열 검정 | 무작위 진입 기준선 분포에서 우리 결과의 위치 | 기준선 초과 |
| MDD | r 0.5% 기준 최대 낙폭 | 보고 (08은 ≤ 15% 권고) |
| SQN | √N × 평균R ÷ R 표준편차. 사실상 t 통계량 | 보고 |
| MAE / MFE | 보유 중 최대 불리·유리 이동 | 손절·익절 위치 진단 |
| 보유 시간, 펀딩 지불액, 미체결률 | — | 보고 |
| 롱·숏 분리 성과 | 방향별 평균 R | 보고 |

- **표본 수의 감**: 진짜 기대값 +0.15R을 확인하려면 약 420건, +0.25R이면 약 150건이 필요하다(단측 α 0.05, 검정력 80%, R 표준편차 약 1.24) (08 §2.9). 우위가 없는 전략도 150건에서 평균 R > 0이 나올 확률이 23%다 (08 §2.9-2).
- **적중률(승률) 기준은 쓰지 않는다.** 손익비 1.5 시스템의 손익분기 승률은 약 40%라서, 적중률 50% 기준은 수익 나는 전략도 떨어뜨린다 [Q4+F10].

### 6.16 freqtrade 교차 검증

- **역할**: G1 판정은 재생기(공용 체결 모델) 결과로 한다. freqtrade는 교차 검증, 누수 점검, 기준선 전략 실행에 쓴다 (ARCHITECTURE C19).
- **기본 가정이 다르다**: freqtrade는 다음 봉 시가 진입, 범위 안이면 슬리피지 없이 체결, 손절은 정확히 손절가에 체결되고 수수료 2배만 더한다. 문서 스스로 "백테스트는 드라이런을 절대 대체하지 못한다"고 적는다 [23](08 §2.7).
- `custom_entry_price`, `confirm_trade_entry`, `check_entry_timeout`, `unfilledtimeout` 콜백으로 계획가·만료·가용성을 어디까지 흉내 낼지는 2단계에서 확인한다 [28] (ARCHITECTURE §10-14).
- 두 결과가 크게 다르면 원인을 찾기 전에는 G1을 판정하지 않는다.
- freqtrade에는 거래소 키를 넣지 않고, freqtrade 텔레그램은 쓰지 않는다 (D10).

## 7. LLM 평가법

### 7.1 무엇을 평가하나

Claude는 관문이 아니라 **분석가·설명자**다(섀도). 의견은 기록만 하고 주문 차단에 쓰지 않는다 (D3, **[결정 필요]**, 추천값 적용 중). 그래서 평가 대상은 다섯 가지다.

| 대상 | 질문 | 절 |
|---|---|---|
| 운영 안정성 | 거절·잘림·검증 실패·폴백·지연·비용이 기준 안인가 | §7.6 |
| 설명의 형식 품질 | 반대 근거·무효화 조건이 비어 있지 않고 규칙을 지키나 | §7.7 |
| 의견의 가치 | "승인 권고/패스 권고"가 코드 메타 필터보다 결과를 잘 가르나 | §7.4 |
| 확신도 보정 | 확신도가 실제 확률과 맞나 | §7.5 |
| 편향 | 롱 쪽으로 치우치나 | §7.6 |

Anthropic의 평가 설계 원칙도 참고한다: 실제 과제 분포를 닮게 하고, 가능하면 자동으로 채점하고, 적은 수의 정밀한 사람 채점보다 **많은 수의 자동 채점**을 우선한다 [14][직접]. LLM으로 채점할 때는 **생성한 모델과 다른 모델**로 채점하라고 권한다 [14][직접].

### 7.3 사후 채점: 모든 신호를

- 승인한 신호뿐 아니라 **패스, 만료, 가드 차단, Claude 실패 신호까지** 공용 체결 모델로 채점한다 (03 §2.4.5, D18).
- 이유 두 가지: ① Claude 의견과 사람 판단의 가치를 따로 잴 수 있다 ② 표본이 약 3배 빨리 쌓인다. 주 10건 채점이면 150건까지 약 15주, 승인한 거래만 주 3건이면 약 50주다 (08 §2.9-3).

### 7.4 Claude 의견 vs 코드 메타 필터 (관문 승격 판정)

- **설계**: 같은 후보에 대해 Claude와 코드 메타 필터(C8)가 각각 "승인 권고/패스 권고"를 낸다(쌍 비교). 메타 필터는 Claude와 **같은 특징 JSON**만 본다 [Q3].
- **통계(제안, G3 전 사전 등록)**:
  - 각자의 분리력 = (승인 권고 신호의 평균 R) − (패스 권고 신호의 평균 R)
  - 판정량 = Claude 분리력 − 메타 필터 분리력
  - 부트스트랩 단측 95% 하한 > 0이면 "Claude가 이겼다"
- **필요한 건수**: 0.25R 차이를 가리려면 집단당 약 304건, 합쳐 약 600건이 필요하다. 계산은 2×(1.645+0.842)²×1.24²÷0.25² ≈ 304다 [계산] (D3).
- **승격 절차**: 이기면 사용자에게 근거와 함께 설명하고 동의를 받은 뒤, G-a 가드에 의견 조건을 켠다(설정 플래그) (ARCHITECTURE §8). 이기지 못하면 Claude는 설명자로 남는다.
- 두 의견의 일치율도 매주 본다. 일치율이 매우 높으면 Claude가 추가 정보를 주지 못한다는 뜻일 수 있다(분석).

### 7.5 확신도 캘리브레이션

| 단계 | 방법 |
|---|---|
| 지금 | 확신도는 **기록만** 한다. 관문은 코드 체크리스트다 (D8, **[결정 필요]**). LLM 확신도는 보정되지 않았다: 금융 VLM ECE 0.25~0.58(검색 요약) [38], 확신도와 정답 상관 ≈ 0 [35] |
| 150건 이상 | 확신도를 0.5~0.6, 0.6~0.7 … 구간으로 나눠 실제 적중률을 그린다(신뢰도 그래프). Brier 점수를 잰다. Brier 하나만 보면 국소적 과신을 놓치므로 그래프와 함께 본다(검색 요약) [39] (03 §2.4.4) |
| 보조 필터 검토 조건 | 확신도-결과 상관이 0.3 이상이고 신뢰구간이 0을 넘으면 보조 필터로 쓸지 사용자와 정한다 (03 §2.4.4) |
| 원칙 | 어떤 경우에도 확신도로 레버리지·수량을 키우지 않는다 (03 §2.4.4) |

### 7.7 설명 품질 점검

- **자동 점검(코드)**: 필수 필드가 있다 · 반대 근거가 1개 이상이다 · 수준 ID가 그 호출의 후보 안에 있다 · URL이 없다 · 길이 제한을 지켰다 · 텍스트 안의 숫자가 입력 JSON에 없는 값이면 "숫자 불일치"로 표시하고 기록한다(제안. 숫자 환각 감시, 03 §2.3-①).
- **사람 점검(주 1회, 5건 표본, 제안)**: "반대 근거가 실제로 판단에 도움이 됐나"를 1~3점으로 매긴다. 자동화 편향을 줄이는 것이 반대 근거의 목적이기 때문이다 (01 §3.2).
- LLM 채점기는 "나중"이다. 쓴다면 생성 모델과 다른 모델을 쓴다 [14].

### 7.8 프롬프트·스키마 버전 관리

| 규칙 | 이유 |
|---|---|
| 파일은 `analyst/prompts/system_vN.md`, `analyst/schemas/output_out-N.json`. **제자리 수정 금지**, 새 버전 파일을 만든다 | 로그의 버전과 파일이 항상 짝이 맞아야 재현할 수 있다 |

### 7.9 모델 교체 절차 (D21)

Opus 5.5는 2027-09-22 이후 퇴역할 수 있다 [18]. G4·G5 기간과 겹칠 수 있다.

1. 새 모델(또는 새 프롬프트·스키마)을 **같은 후보에 섀도로 병행 호출**한다. 버튼에는 쓰지 않는다 (`analyses.kind=SHADOW_MODEL`, ARCHITECTURE §8).
2. 운영 지표(§7.6)와 설명 품질(§7.7)을 쌍으로 비교한다. 의견 분리력은 표본이 충분할 때 함께 본다.
3. 기준을 만족하면 사용자 확인 후 교체한다. 교체 날짜를 결정 기록에 남긴다.
4. Claude가 관문이 아니므로 **코드 규칙 트랙(G1, G4 성과)은 리셋하지 않는다** (D21). 08 문서의 "모델을 바꾸면 G3로 되돌아간다"는 이 절차로 대체됐다 [F07].

### 7.10 사람 기여도 (참고 지표)

- 사람은 최종 승인권자다. 사람의 기여도는 관문이 아니라 **참고 지표**다. 사람의 기여를 가리는 데도 집단당 약 300건이 필요하다 [Q17].
- 볼 것: 승인한 신호와 패스한 신호의 사후 평균 R, 승인율, 결정 시간, 만료율, 패스 사유 코드(시스템 이상 / 뉴스·이벤트 / 데이터 이상 / 기타·직감) 분포 (D5, 07 §2.9.4).
- 승인율이 100%에 가까우면 형식적 승인(고무도장)의 신호다. "기타·직감" 사유가 많으면 주간 리뷰에서 따로 본다 [Q17].

### 8.1 기준표 (D17, 사전 등록한 단일 기준)

단위는 R배수(비용 포함)이고, G1과 G3는 같은 체결 모델을 쓴다. **아래 (1)~(5)를 모두 충족해야** 6단계로 간다.

| # | 관문 | 통과 조건 |
|---|---|---|
| (1) | G1 코드 규칙 백테스트 | 가용성 마스크를 적용한 표본 밖 기대값 ≥ +0.15R · 부트스트랩 95% 하한 > 0 · PF ≥ 1.2 · 비용 2배에서도 양수 · 무작위 기준선 초과. 추세추종 기준선과의 비교는 보고한다 |
| (2) | G2 테스트넷 | 손절 존재 조회 100% · 손절 없는 포지션 0건 · 중복 주문 0건 · "대기 중 체결 + 봇 종료" 시나리오 통과 |

| (4) | 비용 | 월 고정비 차감 후 기대 손익을 제시하거나, "수업료"로 받아들인다는 사용자 확인 |

### 8.4 G4 운영 점검과 중단 조건

- 기간: 30건 이상 또는 8주 이상. r = 0.25%.
- 점검: 실제 슬리피지 ≤ 가정치(0.05%), 손절 누락 0건, 부분 체결 비율, 마크 가격과 체결가 차이.
- **즉시 페이퍼로 돌아간다**: T5(누적 −15%), 손절 누락 1건, 연패가 몬테카를로 p95(약 12연패) 초과 (08 §2.11).
- 한도 체계 T0~T5는 D8·ARCHITECTURE §2.3을 따른다. 시간 기반 한도(일일, 24시간 3손절)는 다음 날 09:00 KST에 자동 해제되고, 누적 낙폭·보안·기술 킬은 서버에서만(LIVE에서는 두 번째 기기에서만) 푼다 [F15][SEC-03 수정].

### 8.5 G5 확대

- 누적 실거래 100건 이상, 평균 R 신뢰구간 하한 > 0이면 r 0.5%. 이후 올려도 상한 1.0% (08 §2.11).

## 9. 사용자 학습 로드맵

### 9.1 원칙

- **목표는 "코드를 쓰는 능력"이 아니라 "결과를 판정하는 능력"이다.** 수용 시험을 설계하고, CI·리포트를 읽고, 관문 통과 여부를 판단할 수 있으면 된다.
- **필요할 때 배운다.** 단계마다 그 단계에 필요한 개념만 익힌다.
- **보안 경험을 쓴다.** 위협 모델, 최소 권한, 비밀 관리, 사고 대응, 탁상훈련은 이미 강점이다. 이 프로젝트에서 새로 배울 것은 주로 **개발 흐름, 트레이딩, 통계**다.

### 9.3 첫 2주 공통 기초 (0~1단계에 걸쳐)

| 주제 | 목표 수준 | 방법 |
|---|---|---|
| Git·GitHub | PR을 열고, 수용 시험 결과를 보고, 스쿼시 병합하고, 태그를 붙일 수 있다 | 이 저장소에서 문서 PR 1개로 연습 |

### 9.4 Claude에게 배우는 법 (질문 틀)

- "이 PR이 하는 일을 비유로 3줄로 설명해 줘. 코드 용어 없이."
- "이 테스트가 실패하면 어떤 사고를 막는 건지 한 문장으로."
- "내가 코드를 안 읽고 이게 맞는지 확인할 방법 1개만 알려 줘."
- "이 개념을 내가 아는 보안 개념에 빗대서 설명해 줘." (예: 멱등성 ≈ 재전송 공격 방어의 nonce)
- "이 결과가 우연일 가능성을 숫자로 말해 줘. 근거 문서 절도 함께."

### 9.5 몰라도 되는 것

Python 문법을 직접 쓰는 능력, 알고리즘·자료구조, 클래스 설계, Docker·SQLite의 내부 동작, 통계 공식의 유도 과정. 필요하면 그때 Claude에게 묻는다.
