## 1. 핵심 요약 (5줄)

1. **LLM에게 매매를 맡긴 실증 결과는 대부분 손실이거나 "운과 구분되지 않음"이다.** 실제 돈을 건 Alpha Arena 시즌1에서 6개 모델 중 4개가 손실을 냈고 Claude Sonnet 4.5는 −42.01%였다. 시즌1.5에서는 32개 계정 중 6개만 이익이었다(검색 요약). 20년 백테스트(FINSABER)와 누수를 막은 평가 연구도 "LLM 전략의 우위는 사라진다"고 보고한다. → **Claude를 예측기가 아니라 해석·필터·설명 도구로 쓰는 PLAN/STRATEGY 방향은 맞다.**
2. **차트 이미지를 보고 방향을 맞히는 능력은 동전 던지기 수준이다.** Claude Opus 5.5는 차트에서 **값을 읽는 능력**이 크게 좋아졌다(Anthropic 공식 [직접]). 하지만 여러 연구는 VLM(이미지를 보는 LLM)이 캔들 모양보다 **직전 추세에 편승**하고, **롱(매수) 쪽으로 치우친다**고 보고한다. → **코드가 계산한 수치 JSON을 주 입력으로 쓴다.** 이미지는 사람용으로 쓰고, Claude에게 넣을지는 모의매매 A/B 비교로 정한다.
3. **LLM의 대표적 실패 5가지가 모두 우리 시스템에 해당한다.** ① 숫자 환각 ② 같은 입력에 다른 답(Opus 5.5는 `temperature` 설정 자체가 막혀 있음 [직접]) ③ 과신(교정 오차 ECE 0.25~0.58) ④ 학습 데이터 기억에 의한 룩어헤드(Opus 5.5 학습 데이터는 2026-06까지 [직접] → 과거 구간 백테스트는 무효) ⑤ 프롬프트 형식 민감도(정확도 차이 최대 76%p).
4. **설계 권고는 네 가지다.**
   - 모든 숫자는 코드가 계산한다. Claude는 코드가 올린 후보 중에서 **고르고, 체크리스트를 판정하고, 설명**한다.
   - 진입·손절·익절 **가격을 Claude가 직접 쓰지 않게** 한다. 코드가 만든 수준(level) ID만 고르게 한다.
   - 구조화 출력(JSON 스키마 강제)을 쓰고, `stop_reason`을 확인한다. 실패하면 주문하지 않는다(fail-closed).
   - "확신도 0.6"은 LLM이 스스로 말한 숫자라 보정되지 않았다. 보정 전까지는 **코드 체크리스트 점수**로 거르고, LLM 확신도는 기록만 한다.
5. **비용은 부담이 작다.** 1시간봉마다(월 720회) 부르면 Opus 5.5 기준 월 약 **$42~73**이다(추정: 이미지 0~3장, effort low~medium). 코드 사전 필터로 25%만 부르면 **$10~18**이다. Sonnet 5.5는 약 절반, Haiku 4.5는 약 1/6이다. 다만 Haiku 4.5는 **2026-10-15 이후 퇴역할 수 있어** 주력으로 권하지 않는다 [직접]. 호출 간격이 60분이라 프롬프트 캐싱 절감은 월 최대 약 $11로 작다. 지연은 호출당 30~60초로 추정되어 1시간봉에는 문제가 없다. **권고: Opus 5.5(effort medium으로 시작해 low와 비교), 월 지출 한도 설정, Batch API는 실시간 신호에 쓰지 않는다.**

| 시점 주의 | 공개 실험 대부분은 **2025년 모델**(Sonnet 4.5, Opus 4.7 등)로 했다. 지금 권장 모델인 Opus 5.5를 트레이딩 판단으로 검증한 공개 연구는 **찾지 못했다(확인 필요)** |

**용어 풀이 (처음 한 번만)**
- **LLM**: 대형 언어 모델. Claude 같은 AI다.
- **VLM(시각언어모델)**: 이미지도 입력으로 받는 LLM이다. Claude도 해당한다.
- **토큰**: LLM이 글을 쪼개 세는 단위다. 비용과 속도가 토큰 수에 비례한다. 영어는 대략 4글자가 1토큰이다 [4].
- **환각(hallucination)**: 입력에 없는 사실이나 숫자를 그럴듯하게 지어내는 것.
- **캘리브레이션(보정)**: "확신도 70%"라고 말한 신호가 실제로 약 70% 맞는지 맞추는 일. 맞지 않으면 "과신" 또는 "과소신"이다.
- **ECE(기대 보정 오차)**: 말한 확신도와 실제 정답률의 평균 차이. 0이면 완벽하고 클수록 나쁘다.
- **룩어헤드 편향**: 그 시점에는 알 수 없던 미래 정보가 섞여 성과가 부풀려지는 현상.
- **구조화 출력(structured outputs)**: 응답을 미리 정한 JSON 형식으로 **강제**하는 API 기능 [2].
- **프롬프트 캐싱**: 매번 똑같이 보내는 앞부분을 서버가 기억해 두었다가 싸게 재사용하는 기능 [3].
- **effort**: Claude가 얼마나 깊이 생각할지 정하는 설정(low~max). 낮을수록 빠르고 싸다 [6].
- **refusal(거절)**: 안전 분류기가 요청을 거절한 응답. 오류가 아니라 정상 응답(HTTP 200)에 `stop_reason: "refusal"`로 온다 [5].
- **페이퍼 트레이딩 / 섀도 모드**: 실제 주문 없이 신호와 결과만 기록하며 검증하는 운영 방식.

**소결**: 반대 방향(LLM 자율 매매가 꾸준히 이긴다)의 근거는 찾지 못했다. 좋은 결과도 단일 시즌이나 단일 모델 한정이다.

### 2.2 실증 ②: LLM 금융 예측과 차트 이미지 이해 연구

핵심 구분: **"차트에서 값을 읽는 능력"**(예: 이 봉의 종가가 얼마인가)과 **"차트를 보고 앞으로의 방향을 맞히는 능력"**은 다르다. 앞의 것은 좋아졌지만 뒤의 것은 여전히 약하다.

| 근거 | 내용 | 신뢰도 |
|---|---|---|
| **Anthropic Vision 문서** [1] [직접] | 한계로 "공간 추론: 좌표·위치 출력은 **근사치**", "개수 세기: 작은 물체가 많으면 **정확하지 않을 수 있음**", "저품질·회전·200px 미만 이미지는 **환각이나 실수** 가능"을 든다. 그리고 "고위험 용도에서는 이미지 해석을 **반드시 검토·검증**하고, 완벽한 정밀도가 필요한 작업에는 **사람 감독 없이 쓰지 말 것**"이라고 적는다. 권장 사항: **이미지를 텍스트보다 앞에** 두기, 흐리거나 과도하게 압축된 이미지 피하기 | 높음 (1차 출처) |
| **Opus 5.5 공식 문서** [7][8] [직접] | "가장 낮은 effort에서도 **밀집 차트에서 값을 읽는** 정확도가 Opus 5 최고 effort보다 높다." "도구 없이 effort를 올리면 기술 도면 판독은 좋아지지만 **차트에는 효과가 거의 없다**." 또 "**틀린 수치를 말하거나 잘못된 출처를 댈 가능성이 훨씬 낮다**" | 높음 (1차 출처). 단, **값 읽기**에 대한 말이지 **방향 예측**에 대한 말이 아니다 |

| **시계열 예측에 LLM이 쓸모 있나 (NeurIPS 2024)** [32] | LLM 기반 시계열 예측법 3개를 분해 실험 | LLM 부분을 **빼거나 단순 어텐션으로 바꿔도 성능이 떨어지지 않았다**(오히려 나아진 경우가 많음). 단, 2026년 대규모 재평가는 반대 결과를 보고해 **논쟁 중**이다 | 중 (검색 요약) |
| **금융 LLM의 낙관 편향** [38] | 여러 연구 | LLM 수익률 예측은 **지나치게 낙관적**이고 신뢰구간이 **너무 좁다**. 이런 편향은 프롬프트로 잘 고쳐지지 않았다 | 중하 (검색 요약) |

**결론**:
- Claude가 차트에서 **숫자를 읽는** 능력은 좋아졌다. 하지만 우리는 그 숫자를 코드로 **정확히** 계산할 수 있으므로, 이미지로 숫자를 읽게 할 이유가 없다.
- 이미지로 **방향을 예측**하게 하는 것은 근거가 약하다(동전 던지기 수준, 추세 편승, 롱 편향).
- 따라서 이미지는 **사람용(텔레그램 알림)**에 쓰고, Claude 입력에 넣을지는 §2.4.5의 **A/B 기록으로 정한다**. 이 결론은 01 §2.3.3, 02 §L과 같다.

### 2.4 설계 모범 사례

#### 2.4.1 역할 분담: 코드가 측정하고, Claude는 해석하고, 사람이 결정한다

| 일 | 담당 | 이유 |
|---|---|---|
| 캔들·거래량·이평·ATR·기준봉·허리·기준가 등 **모든 수치** | **코드** | 매번 같은 결과, 검증 가능, 환각 없음 (§2.3-①) |
| 시나리오 **후보 선별**(L1~L5, S1~S4의 ◎ 조건) | **코드** | STRATEGY §2. 후보가 없으면 Claude를 부르지 않는다 → 비용·알림 피로 감소 |
| 후보 중 **선택 또는 기각** + 체크리스트 항목별 판정(예: "반전 캔들이 맞나", "아는 구간인가") | **Claude** | 코드화하기 어려운(✕·○) 맥락 판단 |
| **반대 근거와 무효화 조건**을 사람 말로 설명 | **Claude** | 자동화 편향 대응(01 §2.4). 사람이 "왜 틀릴 수 있는지"를 봐야 승인이 의미가 있다 |
| 진입·손절·익절 **가격 계산**, 손익비, 수량, 레버리지 | **코드** | Claude가 고른 수준 ID로 코드가 계산한다 |
| 하드 가드(손절 2%, 손익비 1.5, 증거금 20%, 레버리지 3배, 격리, 일일 −5%) | **코드** | Claude·사람 판단과 무관하게 강제 |
| 최종 승인 | **사람** | PLAN §1 |

이 구조는 CIFQA의 "계산은 결정적 도구에" 원칙 [37], Anthropic 비전 문서의 "고위험은 사람 감독" 원칙 [1]과 일치한다.

#### 2.4.2 입력: 이미지 vs 수치

| 항목 | 수치 JSON (코드 계산값) | 차트 이미지 |
|---|---|---|
| 정확성 | 정확하다 | Opus 5.5는 값 읽기가 좋아졌지만 근사치다 [1][8] |
| 방향 판단 기여 | 코드 규칙으로 이미 반영 | 방향 예측 근거가 약하다(동전 던지기 수준, 추세 편승) [12][26][27] |
| 비용 (Opus 5.5) | 3,000토큰 ≈ $0.012 | 1200×700px 1장 = ⌈1200/28⌉×⌈700/28⌉ = **1,075토큰** ≈ $0.0043 [1] |
| 재현성 | 같은 데이터면 같은 입력 | 렌더링 설정(크기·색·기간)이 바뀌면 입력이 바뀐다 → 고정 필수 |
| 사람에게 | 읽기 어렵다 | **직관적이다** → 텔레그램 알림에는 꼭 넣는다 |

**권고**
1. **기본은 수치만** 넣는다. 수치 묶음은 02 §3.4의 필드 표를 따른다.
2. 페이퍼 트레이딩 단계에서 **같은 후보에 대해** "수치만"과 "수치 + 1H 차트 1장"을 **둘 다** 호출해 비교한다(쌍 비교). 두 답이 갈린 사례의 사후 성과로 이미지의 효용을 판단한다.
3. 이미지를 쓴다면 **1장**(1H, 코드가 계산한 기준가·허리 수평선을 그려 넣은 것)부터 시작한다. 3장(4H·1H·15m)은 비용보다 **주의 분산**이 문제다(근거: 없음, 가설).
4. 이미지는 크기·색·봉 개수·축 눈금을 **고정**한다. 가격축 글씨가 읽힐 해상도로 만든다 [1]. 이미지를 텍스트보다 앞에 두는 것이 권장이지만 [1], 캐싱을 위해 수치를 앞에 두는 선택도 가능하다(§2.5.4).

#### 2.4.3 구조화 출력 (JSON 스키마 강제)

공식 문서의 사실 [2] [직접]:
- `output_config.format`으로 JSON 스키마를 주면 **제약 디코딩**으로 형식을 보장한다. "항상 유효한 JSON, 필수 필드 보장, 스키마 위반 재시도 불필요."
- **지원하지 않는 것**: 숫자 범위(`minimum`·`maximum`), 문자열 길이·패턴, `oneOf`, 재귀 스키마 등. → **확신도가 0~1 안인지, 가격이 말이 되는지는 코드가 따로 검사**해야 한다.
- **지원하는 것**: `enum`(문자열·숫자·불리언), `additionalProperties: false`(필수), 날짜 형식 등.
- 스키마를 처음 쓸 때 **컴파일 지연**이 있고, 24시간 캐시된다. **스키마를 바꾸면 프롬프트 캐시가 무효화**된다.
- 문서는 거절·`max_tokens` 중단 시 스키마를 지키는지 **명시하지 않는다** → `stop_reason` 확인이 먼저다.
- Opus 5.5는 assistant prefill(응답 앞부분 미리 채우기)과 강제 도구 호출(`tool_choice: any/tool`)이 **400 오류**다 [7][9]. 형식 강제는 구조화 출력으로 한다.

**STRATEGY §6 JSON에 대한 수정 제안** (개념 설계, 코드 아님)

| 현재 (§6) | 문제 | 제안 |
|---|---|---|
| `entry`, `stop_loss`, `take_profit`에 Claude가 **가격 숫자**를 쓴다 | 숫자 환각. 코드가 "거부"하는 방어는 있지만 애초에 틀릴 여지를 없애는 편이 낫다 | `entry_level_id`, `stop_level_id`, `target_level_ids`에 코드가 준 **수준 ID를 enum으로** 고르게 한다. 가격은 코드가 채운다 |
| `key_levels` 숫자를 "그대로 복사" | 복사 과정에서도 틀릴 수 있다 | 복사하지 않는다. ID로 참조한다 |
| `scenario` 문자열 | 후보 밖 값이 나올 수 있다 | **그 호출에서 코드가 올린 후보 + NONE**만 enum으로 넣는다(호출마다 스키마가 바뀌면 캐시가 깨지므로, 전체 목록 enum + 코드 검증으로 대체해도 된다) |
| `confidence` 0.0~1.0 | 보정되지 않은 자기 평가 [30][31] | 유지하되 **기록 전용**. 알림 기준은 아래 체크리스트 점수 |
| (없음) | — | `checklist`: 항목별 `yes / no / unclear` enum (예: 4H 방향 일치, 건강한 조정, 반전 캔들 확인, 아는 구간, 반대 근거 없음). **코드가 점수화**한다 |
| `evidence`, `summary` | 긴 추론을 요구하면 `reasoning_extraction` 거절 위험 [8] | "근거 3개 이내, 각 한 문장"으로 짧게 제한한다(스키마 `maxItems`는 미지원이므로 프롬프트 지시 + 코드 절단) |
| (없음) | — | `counter_evidence`: 이 신호가 틀릴 수 있는 이유 1~2개 (자동화 편향 대응) |

#### 2.4.4 확신도 캘리브레이션

| 단계 | 방법 | 근거 |
|---|---|---|
| 0. 지금 | "확신도 < 0.6이면 관망"을 **LLM 확신도가 아니라** 체크리스트 점수로 바꾼다. 예: 5항목 중 `yes` 4개 이상 + `no` 0개일 때만 알림. LLM 확신도는 기록만 한다 | 언어화된 확신도 과신 [30][31], 상관 ≈ 0 [12] |
| 1. 선택적 강화 | 코드 후보가 있을 때만 **같은 입력으로 2회** 호출한다. 두 답의 방향·시나리오가 **일치할 때만** 알림을 보낸다. 불일치 자체를 "불확실" 신호로 기록한다 | 자기일관성(여러 답의 일치)이 신뢰도를 높이고 과신을 줄였다 [31][40]. 비용은 약 2배(§2.5.3) |
| 2. 신호 150건 이상 | 확신도를 0.5~0.6, 0.6~0.7 … 구간으로 나눠 **실제 적중률**을 그린다(신뢰도 그래프). **Brier 점수**(확신도와 실제 결과(0/1)의 평균 제곱 오차, 0이 최고)를 잰다 | Brier·신뢰도 그래프는 표준 방법이다. Brier 하나만 보면 국소적 과신을 놓치므로 그래프와 함께 본다 [41] |
| 3. 보정 후 | 확신도-적중률 상관이 0.3 이상이고 신뢰구간이 0을 넘으면, 그때 LLM 확신도를 **보조 필터**로 쓸지 결정한다 | gist의 운영 투입 기준 차용 [12] |
| 원칙 | 어떤 경우에도 확신도로 **레버리지·크기를 키우지 않는다** | Alpha Arena의 설계와 결과 [13][15][17] |

#### 2.4.5 신호 로그와 사후 채점

**(1) 기록할 것 — 신호 1건마다** (SQLite 한 행 + 원본 JSON 파일)

| 묶음 | 필드 |
|---|---|
| 식별 | 신호 ID, 캔들 마감 시각(UTC), 기록 시각 |
| 재현 | 입력 스냅샷(코드 계산값 전체), 이미지 파일 해시, **프롬프트 버전**, 스키마 버전, 모델 ID, effort |
| 모델 응답 | 원본 응답 전체, `stop_reason`, `usage`(입력·출력·캐시 토큰), 지연 시간, 폴백 여부 |
| 판단 | 코드 후보 목록, Claude 선택(시나리오·방향·체크리스트·확신도), 코드 가드 결과(통과/차단 사유) |
| 사람 | 알림 발송 여부, 버튼(롱/숏/패스), 승인까지 걸린 시간, 만료 여부 |
| 결과 | 가상 체결가, 결과 라벨, 결과 R배수(손익 ÷ 1회 위험), 최대 유리 이동(MFE), 최대 불리 이동(MAE), 수수료 반영 여부 |

**중요**: 사람이 **패스한 신호**, Claude가 **관망으로 돌린 후보**, 가드에 **막힌 신호**도 똑같이 결과를 채점한다. 그래야 "Claude의 거르기"와 "사람의 거르기"가 도움이 됐는지 따로 잴 수 있다.

**(2) 채점 규칙 (제안)**
- 신호 시점 가격에서 진입했다고 가정한다. **익절가·손절가·시간 제한(예: 1H 24봉)** 중 먼저 닿은 것으로 결과를 정한다.
- 한 봉 안에서 익절과 손절이 모두 닿으면 순서를 알 수 없다. 1분봉으로 순서를 확인하거나, 확인 못 하면 **손절로 친다**(보수적).
- 결과는 승/패보다 **R배수**로 기록한다. 손익비 1.5에서는 승률만으로 판단할 수 없기 때문이다.

**(3) 볼 지표**

| 지표 | 의미 | 판단 기준 (제안) |
|---|---|---|
| 기대값(평균 R) | 신호 1건당 평균 몇 R을 버는가 | > 0, 그리고 신뢰구간 하한 > 0 |
| 승률 + 윌슨 신뢰구간 | 표본이 작을 때의 불확실성 표시 | 손익비 1.5의 손익분기 승률은 **40%**(비용 0 가정). 왕복 비용이 손절 폭의 5%면 **42%**, 10%면 **44%** (추정) |
| 최대 낙폭 (R 누적) | 최악 구간의 손실 | 일일 −5% 한도와 비교 |
| Brier 점수·신뢰도 그래프 | 확신도 보정 상태 | §2.4.4 |
| 롱·숏 비율 격차 | 방향 편향 | < 10%p |
| **Claude 기여도** | Claude가 통과시킨 후보 vs 기각한 후보의 평균 R 차이 | 차이가 없으면 Claude 필터는 가치가 없다 → "코드 후보 + Claude는 설명만"으로 축소 |
| **이미지 기여도** | "수치만" vs "수치+이미지" 답이 갈린 사례의 평균 R | 차이가 없으면 이미지를 뺀다 |
| **사람 기여도** | 승인한 신호 vs 패스한 신호의 평균 R | 형식적 승인(고무도장) 점검 (01 §2.4) |
| 운영 | 거절률, 스키마·검증 실패율, 평균 지연, 월 비용 | 거절·실패 > 2%면 원인 조사 (기준은 제안값) |

**(4) 얼마나 모아야 판단할 수 있나** (단측 검정 α=0.05, 검정력 80%, 계산값)

| 확인하려는 것 | 필요한 신호 수 |
|---|---|
| 승률 52%가 손익분기 42%보다 높다 | 약 **152건** |
| 승률 50%가 손익분기 42%보다 높다 | 약 **238건** |
| 승률 60%가 50%보다 높다 | 약 **153건** |
| 승률 55%가 50%보다 높다 | 약 **617건** |

→ 사전 필터 후 하루 1~3건이라면 150건에 **2~5개월**이 걸린다(추정). 테스트넷 1~2주(PLAN §6 단계 7)로는 **통계적 판단이 불가능하다**. 1~2주는 "시스템이 제대로 도는지" 확인용으로만 쓴다.

- **비용의 대부분은 출력(생각 토큰 포함)**이다. Opus 5.5 medium, C 구성에서 입력은 $0.041, 출력은 $0.060이다. → 이미지 장수보다 **effort와 호출 횟수**가 비용을 좌우한다.
- **2회 호출 일치 확인**(§2.4.4-1)을 쓰면 해당 호출 비용이 약 1.7배다. 같은 시간 안의 두 번째 호출은 캐시를 읽으므로 입력 비용이 거의 없고, 출력 비용만 한 번 더 낸다. 예(추정): Opus medium, C 구성에서 첫 호출은 5분 캐시 쓰기 포함 $0.111, 두 번째 호출은 $0.062다. 매시 2회면 월 약 **$125**, 사전 필터 후 2회면 월 약 **$31**이다.
- **A/B 쌍 비교**(§2.4.2-2, 수치만 + 이미지 1장을 둘 다 호출)는 사전 필터 기준 Opus low로 월 약 $22(= $10.4 + $11.2)다.
- 참고로 속도 제한은 문제가 되지 않는다. Start 등급에서도 Opus 5.5는 분당 1,000회까지 허용한다 [11]. 다만 새 조직은 이보다 낮은 평가(Evaluation) 등급에서 시작할 수 있다 [11].

#### 2.5.4 프롬프트 캐싱 효과 — "우리 호출 간격에서는 작다"

공식 사실 [3][4] [직접]:
- 최소 캐시 길이: Opus 5.5·Sonnet 5.5 **512토큰**, Haiku 4.5 **4,096토큰**. 짧으면 오류 없이 **조용히 캐시되지 않는다**.
- 수명: 기본 5분, 선택 1시간. 수명은 **요청 시작 시점부터** 잰다. 읽을 때마다 무료로 연장된다.
- 비용: 쓰기 1.25배(5분) / 2배(1시간), 읽기 0.05배(Opus 5.5) 또는 0.1배.
- 이미지도 캐시할 수 있다. effort 값이나 `output_config.format`(스키마)을 바꾸면 캐시가 깨진다 [2][3][6].

우리 상황 분석 (추정):
- 1시간봉 호출은 **시작 간격이 정확히 60분**이다. 5분 캐시는 당연히 만료되고, 1시간 캐시도 경계선이라 **대부분 적중하지 못한다**. 공식 가이드도 "간격이 1시간을 넘으면 어느 쪽도 직접 도움이 되지 않는다"고 적는다(스킬 문서 기준).
- 설령 매번 적중해도 절감액은 시스템 프롬프트 4,000토큰 × 720회 × ($4 − $0.20) = **월 최대 약 $11**(Opus 5.5)이다. 반대로 **적중하지 않는데 캐시를 켜면 쓰기 할증(1.25배)만 낸다.**
- **캐싱이 확실히 이득인 경우**: 같은 시간 안에 여러 번 호출할 때다(실패 후 재시도, 2회 일치 확인, A/B 쌍 호출). 이때는 두 번째 호출부터 시스템 프롬프트와 수치 입력을 0.05배로 읽는다.
- 설계 규칙: 순서를 **[고정 시스템 프롬프트] → [수치 요약] → [이미지] → [짧은 지시]**로 둔다. 시각·ID 같은 바뀌는 값은 **뒤쪽**에 둔다. 적중 여부는 `usage.cache_read_input_tokens`로 확인한다.
- Haiku 4.5는 시스템 프롬프트가 4,096토큰 미만이면 캐시가 아예 안 된다.

#### 2.5.5 지연 시간

| 모델 | 공식 상대 지연 [10] [직접] | 출력 속도 (검색 요약) [42] | 호출당 예상 (추정: 출력 3,000토큰) |
|---|---|---|---|
| Opus 5.5 | Moderate (보통). Opus 5보다 출력이 30% 이상 빠르다 [8] | 약 93토큰/초 (max effort 측정치) | 약 **30~60초** |
| Sonnet 5.5 | Fast | 약 139토큰/초 | 약 20~40초 |
| Haiku 4.5 | Fastest | 80~120토큰/초 (출처마다 다름) | 약 10~20초 (출력 800토큰) |

- 1시간봉 신호, 15분 유효시간(PLAN §4.2)이라면 **1분 안팎의 지연은 문제가 없다.** 타임아웃은 120초 정도로 두고, 넘으면 그 시간 신호는 **건너뛴다**(fail-closed).
- 구조화 출력은 **처음 쓰는 스키마에서 컴파일 지연**이 있다 [2]. 배포 직후 첫 호출은 느릴 수 있다.
- **Batch API**(50% 할인)는 비동기라 결과가 늦게 온다. **실시간 신호에는 쓰지 않는다.** 주간 성과 요약 보고서처럼 기다려도 되는 작업에만 쓸 수 있다. 과거 구간 LLM 백테스트를 Batch로 싸게 돌리는 것은 **룩어헤드 때문에 무의미**하다(§2.3-④).

#### 2.5.6 거절(refusal)·오류 처리 흐름 [5][7][8] [직접]

| 상황 | 신호 | 처리 |
|---|---|---|
| 정상 | `stop_reason: "end_turn"` | 스키마 파싱 → 코드 검증(범위·ID·후보 포함 여부) → 하드 가드 → 알림 |
| 거절 | `stop_reason: "refusal"` + `stop_details.category` | **주문·알림 없음.** "분석 실패(거절)"로 기록하고 텔레그램에 짧게 통보한다. 부분 출력은 **버린다** |
| 잘림 | `stop_reason: "max_tokens"` | 실패로 처리한다. `max_tokens`는 생각 토큰까지 포함하므로 **넉넉히**(예: 16,000) 잡는다 [8] |
| 검증 실패 | 확신도 범위 밖, 없는 ID, 후보 밖 시나리오 | 실패로 처리한다. 재시도는 1회까지 |
| API 오류 | 429(속도·지출 한도), 5xx, 타임아웃 | 이번 신호 건너뜀. 지출 한도 도달은 `error_code: enforced_spend_limit_reached`로 구분된다 [11] |

- **폴백(다른 모델로 자동 재시도)**: `fallbacks: "default"`와 베타 헤더 `server-side-fallback-2026-07-01`을 쓰면, API가 거절 범주에 맞는 추천 모델로 한 번에 재시도한다(Claude API 전용, 베타, **Batch 미지원**) [5]. `reasoning_extraction` 거절은 재시도하지 않는다 [8].
- 거절 과금 [5]: 출력 전에 거절된 경우 `cyber`·`general_harms`·범주 없음은 **과금하지 않는다**. `bio`·`frontier_llm`·`reasoning_extraction`은 **과금한다**. 우리 용도(시세 분석)에서 거절은 드물 것으로 보이지만(추정), 분류기는 무해한 요청도 걸 수 있으므로 처리는 반드시 넣는다.
- 폴백으로 **다른 모델이 답한 신호**는 로그에 표시하고 A/B 통계에서 **분리**한다(모델이 다르면 다른 실험이다).

### 3.4 사용자 결정이 필요한 질문

1. **모델**: Opus 5.5(권장, 사전 필터 시 월 $10~18)로 갈까요, Sonnet 5.5(약 절반)로 갈까요? Haiku 4.5는 곧 퇴역할 수 있어 권하지 않습니다.
2. **호출 방식**: 매시 무조건 호출(월 $42~73) 대신 **코드 후보가 있을 때만** 호출하는 방식(월 $10~18)에 동의하시나요? (STRATEGY §2와 같은 방향)
3. **확신도 0.6 규칙**을 "체크리스트 5개 중 yes 4개 이상, no 0개"로 바꾸는 데 동의하시나요?
4. **2회 호출 일치 확인**(비용 약 2배, 알림 수 감소)을 켤까요? 페이퍼 단계에서만 켜고 효과를 볼 수도 있습니다.
5. **실거래 전환 기준**을 숫자로 정할까요? 예: 페이퍼 150건 이상, 평균 R의 95% 신뢰구간 하한 > 0, 롱·숏 격차 < 10%p, 거절·실패율 < 2%.
6. 나중에 **뉴스·X 게시물** 같은 외부 텍스트를 넣을 계획이 있나요? 있다면 인젝션 방어(§2.3-⑧)를 설계에 먼저 넣어야 합니다.
