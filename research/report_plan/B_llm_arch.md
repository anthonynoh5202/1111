## 0. 결론 (먼저 읽을 것)

1. **권장안은 (b) "변화 감지형"이다.** 매시간 보고는 계산 엔진(코드)이 만들고, Claude Opus 5.5의 전체 분석(세 관점 + 최종안)은 **매일 09:00 KST + 구조가 바뀌거나 조건이 맞을 때만** 부른다(하루 평균 3~5회, 상한 8회 (추정)). Claude 비용은 **월 약 $60~85**(캐시 갱신 켬, 하루 3~5회)다. 예산 $300의 20~28%다.
2. **(a) 매시간 Opus 전체 분석은 권하지 않는다.** 1시간 캐시를 잘 써도 월 약 **$262**(출력 1만 토큰 가정, 범위 $175~387)다. 예산의 87%이고, 출력이 길어지면 넘친다. 돈의 대부분($144)은 바뀐 것이 없는데도 같은 결론을 다시 쓰는 출력값이다. 결론이 시간마다 흔들릴 위험도 크다.
3. **1시간 캐시는 "정확히 60분 간격"이면 믿을 수 없다.** 수명은 요청 시작부터 재며 60분은 만료 경계다 [문서]. 놓치면 1시간 쓰기(입력값의 2배, 6만 토큰에 회당 $0.48)를 다시 낸다. **매시 30분에 `max_tokens=1` 갱신 요청**을 보내면 회당 $0.012로 항상 적중한다. 이것만으로 (a)의 입력 쪽 비용이 월 $239 → $55로 준다.
4. **기준서 두 파일은 약 5만 토큰(추정 범위 4만~6.5만)이다.** 옛 Claude 토크나이저로 재면 50,153토큰(글자당 약 1.0)이다. Opus 5.5의 새 토크나이저는 약 30% 더 나올 수 있다 [문서]. 고정 접두부 전체(지시문·형식 설명 포함)는 **약 6만 토큰**으로 잡았다. 키가 생기면 `count_tokens`(무료 [문서])로 정확히 잰다.
5. **AI는 가격 숫자를 쓰지 않는다.** 엔진이 준 레벨 ID(L05 등)만 고른다. **레버리지·수량 칸은 응답 형식에 아예 없다.** 프로그램이 계좌·손절 거리·최소 주문으로 계산한다. 검사기(26개 규칙)를 통과하지 못하면 1회 다시 묻고, 그래도 안 되면 **관망**으로 바꾼다.
6. **GLM-5.3의 역할은 둘이다.** ① **독립된 두 번째 의견**: 거부권만 있고, 더 공격적으로는 못 바꾼다. ② **Claude 장애 때 대체**: 이때 최종은 관망까지만 낸다. 비용은 월 약 $10~18이며 Claude 예산과 별도다. GLM은 JSON 스키마를 강제하지 못하고(`json_object`만 [검색]), 한국어 품질과 API 데이터의 학습 사용 여부가 확인되지 않았다. GLM에는 **공개 시세와 공개 기준서만** 보낸다.
7. **⚠ GLM "코딩 플랜"(구독) 키를 봇에 쓰면 약관 위반이다.** 약관은 "자기 앱·봇에서 모델 API를 직접 부르는 데 쓰지 말 것"을 명시한다 [검색]. 반드시 **종량제 API 키**(`api.z.ai/api/paas/v4`)를 쓴다. CLAUDE.md의 "구독 자동화 금지" 원칙과 같은 이유다.
8. **차트 이미지는 AI 입력에 필요 없다.** 우리 그림은 같은 숫자로 그린 것이라 새 정보가 없고, 그림 근거는 검사할 수 없다. 숫자 입력이 기본이다. 그림은 검증 실험의 A/B로만 시험한다. 비용은 회당 약 $0.008로 문제가 아니다.
9. **검증 방법은 네 가지다.** 같은 입력 반복, 상하 반전, 날짜 제거 + 가격 재조정, 2026-07 이후(학습 마감 뒤) 깨끗한 구간이다. Batch(50% 할인)로 최소 세트 약 **$62~120**(1회)이다. 진짜 판정은 앞으로 쌓는 기록 150건 이상이다(03 문서와 같다).
10. **⚠ 경제성.** 계좌가 5만 원(35.7 USDT)인데 AI 비용은 월 $60~85(약 8.4만~11.9만 원)로 계좌의 1.7~2.4배다. 시험 단계의 AI 비용은 "연구비"로 봐야 한다. 더 아끼려면 절약 모드(Opus 하루 2~3회, 월 $41~61)를 쓴다.
11. **analyst.py를 그대로 쓰면 비용 기록이 틀린다.** 캐시 읽기를 0.1배로 계산하지만 Opus 5.5는 0.05배다(2배 과대). 1시간 쓰기(2배)도 반영하지 않는다. `system`에 캐시 표시도 없다 → 구현 때 고친다(§11).

### 1.2 프롬프트 캐시 규칙

| 항목 | 내용 |
|---|---|
| 원리 | 앞부분(접두부)이 **바이트 단위로 같아야** 읽힌다. 순서는 tools → system → messages다. 한 글자만 달라도 그 뒤가 전부 무효가 된다 |
| 수명 | 기본 5분, 선택 1시간(`"ttl": "1h"`). **요청 시작 시각부터** 재고, 생성 시간도 수명에서 빠진다. 읽으면 수명이 다시 시작된다(읽기 값만 낸다) |
| 최소 길이 | Opus 5.5·Sonnet 5.5·Haiku 5.5 모두 512토큰. 짧으면 오류 없이 조용히 캐시되지 않는다 |
| 표시 수 | 요청당 최대 4개. 워크스페이스마다 따로 저장된다 → 봇 전용 워크스페이스 하나로 쓴다 |
| 캐시를 깨는 것 | system 내용, 모델, effort·thinking 설정, `output_config.format`(스키마), 이미지·도구 변경 |
| 미리 데우기 | `max_tokens: 0` 요청은 출력 비용 없이 캐시를 쓰거나 갱신한다. **단 `output_config.format`(구조화 출력)과 같이 쓰면 400 오류다** → 우리는 `max_tokens: 1`을 쓴다(허용 여부는 **첫 실행 때 1회 확인**) |
| 속도 제한 | 캐시 읽기는 입력 토큰 한도(ITPM)에 들어가지 않는다 |
| 확인 | 응답의 `usage.cache_read_input_tokens`가 유일한 증거다. 0이면 어디선가 접두부가 바뀐 것이다 |

### 1.3 사고(thinking)·effort

- Opus 5.5는 적응형 사고가 **항상 켜져 있고 끌 수 없다.** `thinking: disabled`를 보내면 400 오류다. 조절은 `output_config.effort`로만 한다(low~max). **기본값은 medium**이다.
- 사고 토큰은 **출력값으로 청구**된다. `usage.output_tokens_details.thinking_tokens`로 따로 볼 수 있다.
- effort를 바꾸면 캐시가 깨진다 → 경로마다 고정한다. 대화 중 effort 변경(베타)은 쓰지 않는다.
- Opus 5.5에서 강제 도구 호출(`tool_choice: any/tool`)은 400 오류다. sampling 값(temperature)도 받지 않는다. 그래서 같은 입력에도 답이 조금씩 달라질 수 있다 → §9의 반복 시험이 필요하다.
- Haiku 5.5는 effort `high` 이하에서 `thinking: disabled`를 받는다. 매시간 짧은 해설에는 사고를 끄고 쓴다.

### 1.4 구조화 출력(JSON 스키마 강제)의 제약

| 항목 | 내용 | 우리 대응 |
|---|---|---|
| 지원 | 기본 타입, `enum`, `const`, `$ref/$defs`, `required`, `additionalProperties:false`(필수), 간단한 정규식 | 모두 필수 필드, enum 위주 |
| 미지원 | 숫자 범위(min/max), 문자열 길이, 배열 최대 개수, 재귀 | 길이·개수·범위는 **코드 검사기**가 본다 |
| 한도 | 선택 필드 합계 24개, 유니언(anyOf·타입 배열) 16개 | 선택 필드 0개, 유니언 0개로 설계(검사 완료) |
| 순서 | 필수 필드는 스키마 순서대로 나온다 | 관점 근거 → 최종안 순서로 둔다(결론을 맨 뒤에) |
| enum 대소문자 | 대소문자가 다르게 나올 수 있다 | 대소문자 무시 비교 |
| 거절 위험 | "생각 과정을 쓰라"는 필드는 `reasoning_extraction` 거절을 부를 수 있다 | "짧은 근거(60자 이내)"만 요구 |
| 캐시 | 스키마는 처음 쓸 때 컴파일되어 24시간 보관된다. **스키마를 바꾸면 프롬프트 캐시도 깨진다** | 호출마다 바뀌는 enum(그 시각 레벨 ID 목록 등)을 넣지 않는다. ID는 정규식 + 코드로 검사 |

### 1.5 이미지 토큰

- 토큰 수 = ⌈가로 ÷ 28⌉ × ⌈세로 ÷ 28⌉. Claude 4.7 이후(Opus 5.5 포함)는 고해상도 등급이다(긴 변 2,576px, 최대 4,784토큰).
- 예: render.py 기본 그림 1600×1000px → 58 × 36 = 2,088토큰 → Opus 5.5에서 회당 약 $0.0084. 1456×816px → 1,560토큰.
- 문서가 적은 한계: 좌표·위치 판단은 근사이고, 작은 그림·회전된 그림에서 틀릴 수 있다.

### 1.6 속도 제한·지출 한도

- Start 등급에서 Opus 5.5는 분당 4,000요청, 입력 200만 토큰, 출력 40만 토큰이다. 우리 사용량으로는 문제가 없다. 새 조직은 더 낮은 Evaluation 등급에서 시작할 수 있다.
- Start 등급의 월 지출 상한은 $500다. 콘솔에서 **직접 월 한도 $250**(예산 $300보다 낮게)를 걸 것을 권한다. 한도에 닿으면 400 오류(`specified API usage limits`)가 난다. 등급 상한에 닿으면 429(`enforced_spend_limit_reached`)다.

### 4.3 전체 분석을 부르는 조건(트리거)

| 코드 | 조건 | 예상 빈도 (추정) |

| S | 4시간봉 마감 때 구조 변화: 새 확정 스윙, 새 기준봉·기준마디, 마디 죽음, 허리 종가 이탈, 박스·트랩 수 변화 | 0~3/일 |

```
messages = [ user: 사실표 JSON(키 정렬, 결정적 직렬화) + 직전 판단 요약 ]
output_config = {effort: "medium", format: {type: "json_schema", schema: brief_out_v1}}
(thinking 생략 = 적응형, tools 없음, temperature 없음)
```

- system에는 **시각·날짜·가격을 절대 넣지 않는다**(넣으면 매시간 캐시가 깨진다). 바뀌는 것은 전부 user 메시지에 넣는다.
- 재요청은 새 단일 요청으로 보낸다. 같은 system에 user 메시지(사실표 + 직전 답 JSON + 위반 목록)만 바꾼다. 대화 이어 붙이기를 하지 않으므로 사고 블록 보존 문제도 없다.
- 기준서는 고정본이다(CLAUDE.md). 바꾸면 새 버전 → 캐시를 한 번 다시 쓴다($0.48).

### 4.6 지시문 핵심 (블록1 요약)

1. 역할: BTCUSDT 무기한 선물의 1시간 보고 분석가. CP(차트프로)·WY(워뇨띠)·CL(Claude 종합)을 **따로** 판단하고, CL이 최종안을 만든다.
2. 사실: 사실표만 사실이다. 가격은 **레벨 ID로만** 가리킨다. 문장 속 숫자는 `allowed_numbers`의 문자열만 쓴다.
3. 금지: 레버리지·수량·비중 숫자 제안(프로그램 몫), "확실·무조건·100%" [WY-11-2][WY-14-2][CP-23-3], 보조지표 근거 [WY-02-2], 신뢰도 C 자료.
4. 절차: CP는 [CP-25] 점검 순서, WY는 "워뇨띠 관점 절차" 10단계, CL은 같은 점·다른 점 → 최종안. 판단마다 규칙 번호를 붙인다.
5. 미리 알려 주는 결정 규칙(검사기와 같다 → 위반을 줄인다): 쉬는 구간이면 관망 [CP-25-1]. 살아 있는 기준마디 반대 방향 금지, 트랩 예외 [CP-05-3][CP-13-7]. 손절은 절대 기준가, 허리 바로 아래 금지 [CP-17-1][CP-06]. 손익비 T1 ≥ 1, T2 ≥ 2 [CP-25-3][CP-18-2]. 5:5면 관망 [CP-23-1]. "관망도 정상 결론이다".
6. 직전 판단과 달라지면 `changes_vs_prev`에 이유를 규칙 번호와 함께 쓴다 [WY-14-1].
7. 형식: 근거 ≤ 5개(각 60자 이내), 반대 근거 ≤ 3개, 표시 ≤ 18개, 생각 과정은 쓰지 않는다(짧은 근거만).

## 5. 응답 형식 (JSON 스키마 `brief_out_v1`)

전체 스키마: `scratchpad/team/b_tok/scripts/brief_out_v1.schema.json`. 0929 예시(`example_out_0929.json`)로 jsonschema 검사를 통과했다. 선택 필드 0개, 유니언 0개, 범위·길이 제약 없음(구조화 출력 한도 안).

### 5.1 원칙
- **가격 숫자 칸이 없다.** 진입·손절·목표·무효화·표시는 모두 엔진 ID(`L05`, `Z01`, `C03`, `M01`…)다. 가격은 프로그램이 채운다.
- **레버리지·수량 칸이 없다.** 프로그램이 계산해 보고서에 붙인다.
- 모든 필드가 필수다. 관망일 때 ID 칸에는 `"NONE"`을 넣는다(유니언·선택 필드 한도를 피한다).
- 근거(관점들)가 먼저, 최종안이 뒤에 나오도록 순서를 정했다.

### 5.2 필드

| 필드 | 형식 | 뜻 |
|---|---|---|
| `schema_version` | `"brief_out_v1"` | |
| `facts_id` | 12자리 16진수 | 입력 사실표 해시를 그대로 돌려준다 → 어느 입력의 답인지 묶는다 |
| `fact_checks` | waist_side(ABOVE/BELOW/INSIDE/NONE), live_madi(UP/DOWN/NONE), rest_zone(YES/NO), similarity(GATHERED_UP/GATHERED_DOWN/SPLIT/NONE), trend_4h(UP/DOWN/BOX/UNCLEAR) | 모델이 사실을 제대로 읽었는지 엔진 값과 대조한다 |
| `views.CP/WY/CL` | stance(LONG/SHORT/WAIT), setup(18개 enum), regime, evidence[], counter[], one_line | 세 관점별 판단. evidence·counter = {rules: [CP-06-1…], facts: [ID…], text: 60자 이내} |
| `final.decision` | LONG / SHORT / WAIT | 최종 판단(롱/숏/관망) |

| `final.entry_lo`, `entry_hi` | 레벨 ID | 진입 구간 |
| `final.entry_trigger` | LIMIT_IN_ZONE / CLOSE_CONFIRM_1H / CLOSE_CONFIRM_4H / NONE | 지정가인지, 종가 확인 뒤인지 |

| `final.t1`, `t2` | 레벨 ID | 목표 1·2(T1에서 절반 익절 [CP-18-3]) |
| `final.invalidation[]` | {tf, op: CLOSE_ABOVE/CLOSE_BELOW/TOUCH, level, volume: ANY/VR2_PLUS/LOW, rules} | 무효화 조건 |
| `final.valid_hours` | 1/4/8/12/24 | 유효 시간. 프로그램이 `valid_until`로 바꾼다 |
| `final.confidence_band` | LOW/MID/HIGH | 모델 자기 추정(보정 전, 기록용). 보고서 신뢰도는 프로그램이 다시 계산한다(§7.3) |
| `final.watch[]` | 조건 형식은 무효화와 같다 | 관망일 때 "이러면 다시 본다" [CP-25-2][CP-25-6] |
| `final.why_wait[]` | REST_ZONE, RR_LOW, VIEWS_CONFLICT, UNKNOWN_ZONE, MID_RANGE … | 관망 이유 코드 |
| `marks[]` | {no, view: CP/WY/CL, tf, kind: candle/box/level/band/zone/highs/arrow/offchart, refs: [ID], text} | sample_0929.json과 같은 종류. 가격·시각 대신 ID를 쓴다 |
| `changes_vs_prev` | 문자열 | 직전 판단과 바뀐 점 [WY-14-1] |
| `data_gaps[]` | NO_EVENT_CALENDAR, VOLUME_SINGLE_EXCHANGE … | 빠진 자료 |

## 7. GLM의 역할·불일치 표시·위험

### 7.1 역할

| 역할 | 하는 일 | 받는 입력 | 쓰는 때 |
|---|---|---|---|
| **독립 두 번째 의견** | 같은 사실표로 따로 판단 + "지금 판단이 틀릴 가장 강한 이유 3개"(규칙 번호) | 사실표 + 기준서 + GLM용 지시문. **Claude 답·직전 판단은 주지 않는다**(독립성) | Opus 전체 분석 때(월 약 150회) |
| **Claude 장애 대체** | 같은 형식의 대체 분석 | 위와 같음 | Claude 실패 시. 최종은 관망까지만("대체 분석, 참고") |
| 검증 실험의 비교 모델 | 같은 시험(§9)을 GLM으로도 돌린다 | 같음 | 1회성 |
| (안 맡김) 매시간 짧은 해설 | — | — | Haiku 5.5가 값은 비슷하고 한국어·정책이 더 단순하다 |

- GLM 문장은 한국어 품질이 확인되지 않았으므로 **화면에 그대로 쓰지 않는다.** enum·규칙 번호만 받아 템플릿 문장으로 보여 준다. 예: "두 번째 의견: 관망 — 근거 [CP-16-4][CP-14-2]".

### 7.2 두 모델 결론이 다를 때 표시

| Claude 최종 | GLM | 보고서 첫 줄 표시 | 최종 |
|---|---|---|---|
| 롱 | 롱 | "두 번째 의견 일치" | 롱(신뢰도 유지) |
| 롱 | 관망 | "두 번째 의견: 관망 [규칙]" | 롱, 신뢰도 −1 |
| 롱 | 숏 | "⚠ 두 모델 판단 반대(Claude 롱 / GLM 숏)" | **관망** |
| 관망 | 롱·숏 | "두 번째 의견: 롱 [규칙] (참고)" | 관망(GLM은 올리지 못한다) |
| 롱 | 응답 없음·검사 실패 | "두 번째 의견 없음" | 롱, 신뢰도 상한 MID |

(숏은 거울처럼 같다.) 불일치는 전부 기록한다 → "두 모델이 갈렸을 때 누가 맞았나"를 나중에 잰다.

### 7.3 보고서에 보이는 신뢰도 (프로그램 계산)

- 출발점은 모델의 `confidence_band`다. 다음 경우마다 한 단계씩 내린다: GLM 관망, 2차 표본 ID 불일치, WY 반대, 검사기 자동 수정. 다음 경우에는 상한을 MID로 둔다: GLM 없음, 일정표 없음.
- 표시는 말로만 한다: **높음 / 보통 / 낮음**. "높음≈70% 자리 [CP-23-3]", "낮음≈5:5 [CP-23-1]"은 기준서 표현에 맞춘 이름표일 뿐이고 **실제 확률이 아니다**("보정 전" 표시).
- 신호가 150건 쌓이면 등급별 실제 적중률로 바꾼다(03 문서 §2.4.4).

## 9. AI 판단이 맞는지 확인하는 방법

### 9.1 매 호출 자동 검사 (돈 안 듦 또는 이미 포함)
- 검사기 V1~V26, `fact_checks` 대조, 2차 표본 일치(롱/숏일 때), GLM 일치.
- 주간 집계: 검사 통과율, 재요청 비율, 2차 표본 불일치율, GLM 불일치율, 롱·숏 비율 차(10%p 넘으면 경고 — 03 문서), 월 비용.

### 9.2 오프라인 시험 4가지 (Opus, Batch 50% 할인, 1회당 $0.12~0.24)

| 시험 | 방법 | 보는 값 | 합격선(우리 제안) | 규모 → 비용 |
|---|---|---|---|---|
| ① 같은 입력 반복 | 같은 사실표를 5번 보낸다(temperature 조절이 안 돼 사고에서 흔들림) | 결론 일치율, 손절·진입 ID 일치율 | 결론 일치 ≥ 80%, 롱↔숏 뒤집힘 0% | 50입력 × 5 = 250회 → $30~59 |
| ② 상하 반전 | 가격을 창 가운데 M 기준으로 뒤집고(p′ = 2M − p, 고가↔저가), 펀딩 부호를 바꾸고, 엔진을 다시 돌린다. 닮은꼴은 과거 전체를 함께 뒤집어 다시 계산한다 | 롱↔숏·관망↔관망 대응률, 롱/숏 비율 차 | 대응률 ≥ 80%, 비율 차 ≤ 10%p | 50 × 2 × 3 = 300회 → $37~71 |
| ③ 기억 오염 | 날짜를 지우고(상대 시각 "D-12"), 가격에 k배(예: 0.41, 1.73)를 곱한 뒤 엔진을 다시 돌린다. 2026-06 이전 / 이후 시점으로 나눠 원본과 비교한다 | 원본 대 익명 결론 일치율의 차이(이전 − 이후) | 차이 ≤ 10%p. 넘으면 과거 구간 성과는 무효로 본다 | 50 × 2 × 3 = 300회 → $37~71 |
| ④ 깨끗한 검증 | 2026-07-01 이후(학습 마감 뒤) 시점을 재생한다. 트리거 때만 분석하고, 결과를 R배수로 채점한다 | 평균 R·승률·롱/숏 비율 vs "엔진만"·"항상 관망" | 표본이 작아 "이상 없음" 확인용 | 90일 × 4 = 360회 → $44~85 |
| **합계** | | | | **최소 세트 510회 $62~120** / 전체 1,210회 $148~286 |

- 최소 세트: ① 30 × 3, ② 30 × 2 × 2, ③ 30 × 2 × 2, ④ 180시점.
- Batch는 캐시 적중을 보장하지 않는다. 1시간 캐시로 1건을 먼저 보내 쓰고, 끝나면 나머지를 보내는 방법을 쓴다 [문서]. 시험에서는 "직전 판단" 입력을 비워 순서 의존을 없앤다.
- 같은 시험을 GLM으로도 돌린다(약 1/2~1/4 값, GLM 예산).
- 로컬 데이터는 2026-09-28까지다. ④를 늘리려면 사용자 맥에서 바이낸스 데이터를 더 받는다.
- 지시문·모델·스키마를 바꿀 때마다 ①을 다시 돌린다(회귀 점검).
- ③의 한계: 가리기만으로 기억 효과가 다 없어지지는 않는다(03 문서 [35][36]). 그래서 2026-06 이전 구간은 "형식·일관성 점검"에만 쓰고 "돈을 버나" 판정에는 쓰지 않는다.

### 9.3 앞으로 쌓는 기록 (진짜 판정)
- 03 문서 §2.4.5의 신호 기록·채점 규칙을 그대로 쓴다. 모든 분석(관망·검사기가 바꾼 것·사용자가 안 들어간 것 포함)을 R배수로 채점한다.
- 볼 것: 평균 R과 신뢰구간, Claude 기여도(엔진 후보 중 Claude가 고른 것 대 버린 것), GLM 불일치 때 누가 맞았나, 이미지 A/B, 신뢰도 등급별 적중률.
- 판단에 필요한 표본은 약 150건 이상이다(2~5개월).

## 10. 이미지 입력이 필요한가 → **필요 없다(숫자 입력이 기본)**

| 관점 | 숫자만 | 그림 추가 |
|---|---|---|
| 정확성 | 엔진 값 그대로 | 그림에서 값을 읽으면 근사다. 위치 판단도 근사다(공식 한계) |
| 새 정보 | — | 우리 그림은 같은 숫자로 그린 것이라 새 정보가 없다 |
| 편향 | — | 연구: 그림 보고 방향 맞히기는 동전 수준이고, 롱 편향·직전 추세 편승이 있다(03 문서 [12][26]) |
| 검사 | ID·숫자로 검사할 수 있다 | "그림에서 그렇게 보였다"는 검사할 수 없다 |
| 비용 | — | 1600×1000 = 2,088토큰 ≈ 회당 $0.008(월 150회 $1.3). **비용은 이유가 아니다** |
| 기준서의 "감각 영역" | 모양을 숫자로 바꿔 준다(스윙 순서·박스 범위·꼬리 비율·터치 수) | 모양 직관에는 도움이 될 수도 있다 |

- 결정: 숫자만으로 운영한다. §9 시험에서 "숫자만" 대 "숫자 + 표시 없는 깨끗한 4시간봉 그림 1장"을 A/B로 비교한다. 결론 일치율·검사 통과율·성과에서 뚜렷한 이득이 있을 때만 넣는다. 넣을 때는 user 메시지 안에 둔다(캐시 접두부 뒤라 영향 없음).
- 사람에게 보내는 그림·PDF는 프로그램이 AI의 `marks`로 그린다.

## 12. 확인 못 한 것 · 다음 할 일

1. **기준서 실제 토큰 수**: 키가 생기면 `count_tokens(model="claude-opus-5-5")`로 잰다(무료).
2. **`max_tokens: 1` + 구조화 출력 + 항상 켜진 사고**가 허용되는지(캐시 갱신용). 첫 실행 때 1회 확인한다. 안 되면 (b) 유지 없음(5분 쓰기)으로 바꾼다(+약 $18/월).
3. **실제 출력 토큰**(effort medium의 사고량): 첫 20회 `usage`로 비용표를 고친다. effort low·medium·high는 §9 시험 세트로 비교한다.
4. **트리거 빈도**: 엔진으로 과거 데이터에서 센다(비용 0) → 월 비용을 확정한다.
5. **GLM 전부**: docs.z.ai를 직접 열어 다시 확인해야 한다(이 세션에서는 막힘). 확인할 것은 가격·모델 ID·json_schema 지원 여부·캐시 수명·속도 제한 숫자·effort 이름·데이터 학습 사용(서면 확인 권장)이다. 사용자가 가진 GLM이 **코딩 플랜인지 종량제인지** 확인한다.
6. **경제 일정표**(FOMC·CPI) 출처가 없다 → V19는 경고만 한다.
7. Haiku 5.5·GLM의 한국어 품질은 실제 답 20개를 사람이 읽고 정한다.
