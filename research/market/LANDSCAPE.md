## 0. 3분 요약 (먼저 읽기)

1. **완성품은 없다.** "Claude 분석 → 텔레그램에서 신호마다 사람이 승인 → BTC 선물 주문" 흐름을 그대로 주는 오픈소스나 서비스는 찾지 못했다. 가장 가까운 것은 Hummingbot의 텔레그램 도구 Condor와 HKUDS의 Vibe-Trading인데 둘 다 신생이다. 국내에서 유명한 조코딩 gpt-bitcoin은 **현물·레버리지 없음·완전 자동**이라 구조가 다르다 [11][12][28][33].
2. **상용 시그널 서비스(3Commas·Cornix·WunderTrading)와 TradingView 웹훅은 쓰지 않는다.** 거래 키를 제3자 서버에 맡기거나, 외부에서 접속할 수 있는 공개 서버를 열어야 하기 때문이다. 3Commas는 2022-12 키 유출로 약 2,000만 달러 피해가 났다. 피해는 출금이 아니라 **거래 권한**으로 났다(검색 요약) [22].
3. **LLM에게 매매를 맡긴 실험은 대부분 손실이었다.** 실제 돈을 건 Alpha Arena 시즌1에서 6개 모델 중 4개가 손실을 냈고, Claude Sonnet 4.5는 −42.01%였다. 시즌1.5는 32개 계정 중 6개만 이익이었다(검색 요약) [40][43]. 차트 이미지로 방향을 맞힌 정확도는 동전 던지기와 구분되지 않았고, 모델이 말하는 확신도와 정답의 상관은 거의 0이었다 [직접][51]. → **Claude는 매매 관문이 아니라 분석가·설명자로 쓴다** (D3, **결정 필요**).
4. **실행 엔진은 자체 주문 게이트웨이 하나로 한다.** 가장 성숙한 오픈소스 봇 freqtrade(GitHub 스타 54,910)는 우리 주문 사양(주문 만료 시각 지정, 신호별 절대 손절, 손절 존재 대조)과 보안 조건을 동시에 맞추지 못한다. 그래서 **백테스트·드라이런 전용**으로만 쓴다 (D10). 01 문서가 권했던 "freqtrade REST 강제 진입(B2)" 방식은 이 결정으로 대체됐다.
5. **거래소는 바이낸스 USDⓈ-M을 유지한다.** 2026년 상반기 무기한 선물 점유율 약 33~35%로 1위다(검색 요약) [64]. 다만 후보 5곳 모두 사고 이력이 있어서, **보안은 어느 거래소를 고르느냐보다 노출을 얼마나 줄이느냐에서 갈린다.** 예비는 OKX, 그다음 Bybit(어댑터는 '나중'), Bitget은 2026-09-24 해킹으로 제외, Hyperliquid는 연구만 한다 (D6).
6. **한국: "처벌"보다 "접근 차단"이 커지는 위험이다.** 이용자 개인을 처벌하는 규정은 현재 없다(검색 요약). 하지만 앱 차단이 넓어졌고, 웹사이트 차단 기준을 2026-09 말 확정할 예정이다 [84]~[89]. → **회사 규정·차단 기준·차단 시 정책을 0단계 게이트에서 먼저 확인**한다. 세금은 2027-01-01 과세가 정부 방침이지만 국회 의결 전이고, 무기한 선물 손익의 소득 분류는 불명확하다 [98][99]. → 세무 기록은 처음부터 남기고, 세무 상담은 2026-12 국회 의결 뒤에 한다.
7. **남들이 가장 많이 실패한 지점은 두 가지다.** ① 검증하지 않은 신호에 돈을 건다. ② 리스크 통제를 모델이나 서비스에 맡긴다. 그래서 우리는 **코드 규칙이 무작위보다 나은지부터 검증(G1)**하고, **리스크 가드는 코드에**, **사람 승인은 마지막 관문**에 둔다 (D16, D17).

| 쟁점 | 내용 | 근거 |
|---|---|---|
| 주문 사양 불일치 | 우리 주문은 지정가에 **만료 시각(GTD)**을 붙이고, 신호 ID로 **거래소 손절을 즉시** 걸고, 손절이 실제로 있는지 대조한다 (D7). freqtrade의 강제 진입 API에는 GTD 지정이 없고, 거래소 손절 갱신 주기는 기본 60초다 | [4][6], 07 §3.2, 08 §3.1 |

**교훈 두 가지** (01 §2.2)
- 제3자에게 **거래 가능 키**를 맡기는 것 자체가 위험이다. 출금 권한을 꺼도 거래 권한만으로 피해가 난다(3Commas). 그래서 **IP 화이트리스트는 "권장"이 아니라 없으면 실거래 불가인 조건**이다 (D6).
- 웹훅을 받으려면 외부에 공개된 서버가 필요하다. 우리는 텔레그램 **롱 폴링**으로 받아 인바운드 포트 0을 지킨다 (D5).

**관찰** (01 §2.3.1)
- 인기가 가장 많은 LLM 프로젝트(TradingAgents, ai-hedge-fund)는 실제 주문을 내지 않는다. 실거래를 하는 프로젝트는 대개 **"기본은 모의, 실거래는 확인 후"**로 설계되어 있다.
- LLM에게 주문 도구(MCP·툴)를 직접 주는 구조가 늘고 있다(Hummingbot MCP, Condor 에이전트, nofx). 우리는 **Claude에게 주문 도구를 주지 않는다.** Claude는 JSON만 출력하고, 주문은 코드가 가드를 통과한 경우에만 낸다 (D2, D3).

### 2.7 이 절의 결론

- **두뇌(데이터·Claude 분석·텔레그램 승인·하드 가드)와 근육(주문 실행) 모두 우리 코드**로 만든다. 남의 엔진에 얹는 이점(검증된 주문 수명주기)은 크지만, 우리 사양과 보안 조건을 만족하지 못한다. 대신 범위를 **BTCUSDT·One-way·1포지션**으로 좁혀 직접 구현의 위험을 줄인다 (D10).
- 기존 도구에서 가져오는 것은 **백테스트 엔진(freqtrade)**과 **설계 패턴(제안·확인 분리, fail-closed, 상태 머신, 삼중 장벽)**이다.

### 3.4 이 근거가 우리 설계에 준 결론

1. **Claude의 역할 = 분석가·설명자** (D3, **결정 필요**, 추천값 적용 중). 코드가 올린 후보를 요약하고, 반대 근거와 무효화 조건을 쓰고, 코드가 만든 수준 ID를 고르고, "승인 권고/패스 권고" 의견을 낸다. 의견은 **섀도로 기록만** 하고 주문 차단에는 쓰지 않는다.
   - 이유: 수정된 설계에서 Claude는 코드가 계산한 수치만 받으므로 코드보다 정보 우위가 없다. 방향 적중은 우연 수준이고, 확신도와 정답의 상관은 약 0이다 [51][56].
   - 승격 조건: 같은 특징 JSON을 쓰는 **코드 메타 필터(체크리스트 점수)**를 약 600건 비교에서 이길 때만 관문으로 올린다. 0.25R 차이를 가리려면 집단당 약 304건이 필요하다(판정 Q3 재계산).
2. **입력은 수치 JSON이 주재료** (D4). 차트 이미지는 텔레그램에서 사람이 보는 용도다. Claude에게 이미지를 넣을지는 '나중'의 쌍 비교 실험으로 정한다.
3. **Claude 호출은 코드 후보가 있을 때만** (D2). 월 $10~18(추정)로 매시 호출($42~73)보다 싸다 [03 §2.5.3].
4. **검증은 두 갈래.** 코드 규칙은 과거 백테스트(G1), Claude·사람 층은 앞으로 쌓이는 페이퍼(G3, 150건 이상·8주 이상). 우위가 없는 전략도 20건에서는 40% 확률로 이익처럼 보인다 [08 §2.11] (D17).

**계정·키 설정 (D6 그대로)**: 바이낸스 USDⓈ-M BTCUSDT 무기한 선물. **봇 전용 서브계정**, One-way 모드, Single-Asset(USDT) 모드, 격리 마진, 거래소 쪽 레버리지도 3배. 키는 서버에서 만든 Ed25519로, **선물 거래 + 읽기만** 켜고 출금·이체는 끈다. **고정 IP 하나만** 허용한다. 메인 계정에는 출금 주소 화이트리스트와 피싱 방지 코드를 켠다.

**사용자 생각("보안성과 요즘 인기에 따라 거래소를 바꿀 수 있다")에 대한 의견 (분석 의견)**
- 방향은 맞다. 다만 모든 후보에 사고 이력이 있고, 개인 봇 계정의 가장 큰 위험은 키 탈취와 봇 버그다. **보안 차이는 거래소보다 우리 운영 방식에서 더 크게 난다.**
- 그래서 **"기본 거래소는 하나, 교체 준비는 하나 더"**가 현실적이다. 처음부터 여러 거래소에 주문하면 테스트와 보안 표면이 두 배가 된다. 교체 사유(차단, 입금 경로 단절 등)가 생기면 그때 예비 어댑터를 켠다.

### 5.4 남들이 잘 안 하는데 우리가 하는 것 (차별점)

1. **신호마다 사람 승인 + 승인 시점 재계산**: 확인 화면에서 서버가 가격·손익비·위험을 다시 계산하고, 괴리가 크면 취소한다 (D5, D8).
2. **돈을 걸기 전에 엣지부터 검증**: 코드 규칙 G1 → 섀도·페이퍼 G3 → 테스트넷 G2 → 소액 실거래 G4 순서. 통과 규칙이 0개면 멈추고 재설계한다 (D16, D17).
3. **패스·만료·차단된 신호까지 사후 채점**: Claude·사람 기여도를 따로 잰다. 하나의 체결·채점 모델(신호 시각 + 지연 + 지정가 관통 체결 + 만료)을 백테스트·페이퍼·실거래에 똑같이 쓴다 (D18, PLAN §3.5).
4. **보안 담당자 관점의 설계**: 인바운드 0, Ed25519 서버 생성 키, 주문 방화벽, 손절 존재 대조, 서버 침해 피해 상한, 서버 밖 감시자, 탁상훈련 (D6, D7, D14, D15).
